An agent meets a TypedPress project in two places: while the project is being
written, and when the app runs. TypedPress has an MCP server for each:

| | Development time | Runtime |
|---|---|---|
| What it is | `typedpress mcp`, in the `typedpress` binary | the site's endpoint, `/wp-json/mcp/typedpress-<app>` |
| Who uses it | a coding agent working on the project's source | any agent using the app's data and actions |
| Transport | stdio | Streamable HTTP |
| What it answers | the project's schema, compiler diagnostics, TypedPress's documentation, the command table, the dev site | one tool per collection operation and action |
| Access | the local files, and the local dev site | a WordPress user's access rules |

`typedpress init` sets the first one up in a project, with an `AGENTS.md` section and
the skills that carry the step-by-step procedures. This page is the reference
for both servers; the procedures are in the skills.

## Set a project up for coding agents: `typedpress init`

`typedpress init [dir]` writes what a coding agent needs into the project. A project
made with `npm create typedpress` already has them: the scaffolder runs
`typedpress init` once the compiler is installed.

| File | What it is |
|---|---|
| `AGENTS.md` | A section between `<!-- typedpress:begin -->` and `<!-- typedpress:end -->`: this project's kinds with their fields, access rules and API paths, its actions, jobs, pages and routes, the roles, the site's endpoints, every `typedpress` command, and the skills. |
| `.mcp.json` | A server named `typedpress` that starts `typedpress mcp` (below). |
| `.agents/skills/`, `.claude/skills/` | The skills this compiler carries, one per task (below). |
| `.github/workflows/typedpress-sync.yml` | Only with `typedpress init --github`: the workflow that keeps synced content and the site in step through pull requests ([Content in git](https://github.com/spacefast/zero/blob/main/docs-site/docs/publishing/content-in-git.mdx)). It is at the repository's root even when the project is in a folder of it. |

The section is generated from the compiled project and from the command table,
so it describes this project, not TypedPress in general. Commit all of it.

The skills are in the layout of
[WordPress/agent-skills](https://github.com/WordPress/agent-skills): a
directory per skill with a `SKILL.md` whose front matter says when to use it.
Each is a short procedure that links to the documentation for depth:

| Skill | Task |
|---|---|
| `typedpress-add-kind` | Add a kind or a field, a `ref()`, an access rule; rename or remove a field. |
| `typedpress-write-action` | Write an `action()` or a `job()`. |
| `typedpress-add-page` | Add a page, a layout or an HTTP route under `tp/app/`. |
| `typedpress-fix-diagnostic` | Read a compiler diagnostic and fix its cause. |
| `typedpress-dev-site` | Run the local dev site and inspect it. |
| `typedpress-connect-mcp` | Connect an MCP client to a site's runtime endpoint. |
| `typedpress-migrate` | Convert a Zero 0.8 app, or import another CMS's schema. |

- Text outside the two markers in `AGENTS.md` is yours. A rerun replaces the
  section and nothing else. A marker counts only on a line of its own, so prose
  that quotes one is left alone.
- A server already named `typedpress` in `.mcp.json`, and every other server, is
  left as it is. The entry is inserted into the file's text, so its formatting
  and numbers are unchanged.
- The skill files are TypedPress's: a rerun writes them back as this compiler has them.
  Delete `.claude/skills` or `.agents/skills` if you do not use that agent; a
  rerun does not bring it back.
- Files keep their permissions, and an `AGENTS.md` that links to another file of
  the project (`CLAUDE.md`) is written through the link. A skills directory that
  links outside the project is refused, before anything is written.
- The workflow is TypedPress's while its first line says `typedpress init --github` wrote it for this
  project: a rerun (with or without `--github`) writes it back when the synced folders change.
  Another project in the same repository leaves it alone. Delete that line to keep your own edits;
  it is never touched again.
- A project with its own `CLAUDE.md` should import the file with a line
  `@AGENTS.md`; `typedpress init` says so when it is missing.

When the config or the compiler changes, the files go out of date. `typedpress check`,
`typedpress build` and `typedpress dev` then print one line:

```text
hint: AGENTS.md and the agent skills no longer match this project or this compiler; run typedpress init to update them
```

Only a project that ran `typedpress init` gets the hint. In CI, `typedpress init --check`
writes nothing, names each file that would change, and exits 1 when there is one.

## Develop a project with a coding agent: `typedpress mcp`

`typedpress mcp [dir]` serves the project in `dir` (default: the current directory)
to a coding agent on stdin and stdout. `typedpress init` registers it in `.mcp.json`.
To register it by hand, for Claude Code, in the project's `.mcp.json`:

```json
{
  "mcpServers": {
    "typedpress": { "command": "npx", "args": ["--no-install", "typedpress", "mcp"] }
  }
}
```

For Codex: `codex mcp add first -- npx --no-install typedpress mcp`. `--no-install`
runs the `typedpress` the project already has from `typedpress` and never
downloads a package by that name. With a compiler built from source, use its
path in place of `npx --no-install typedpress`.

| Tool | What it returns |
|---|---|
| `schema` | The project's kinds with their fields, access rules, relations and hooks; globals, actions, jobs, pages and HTTP routes, file buckets, roles, the Abilities the site registers, and the endpoints. `kind` narrows it to one kind. |
| `check` | The `typedpress-diagnostics` envelope `typedpress check --json` prints ([compiler diagnostics](https://github.com/spacefast/zero/blob/main/docs/compiler-diagnostics.md)). It writes nothing. |
| `docs_search`, `docs_read` | TypedPress's documentation as built into this binary: the guides in `docs/` (not the design proposals or the pages for hosts and maintainers) and the docs site's pages. A long page or section read whole answers with its opening and its sections; pass `section` to read one. |
| `commands` | The command table `typedpress help` prints. |
| `dev_status` | What `typedpress dev status --json` reports: whether the project has a local dev site, whether it runs, its URL and port, and whether a `typedpress dev` process is rebuilding it on save. |
| `query` | A kind's records from the local dev site, through `typedpress find`: `kind`, `where`, `orderBy`, `limit` (20 by default, at most 500), `offset`, `columns`, `with`. Like every request to the site, it first publishes scheduled posts that are due. |

`schema`, `check`, `docs_search` and `docs_read` compile or read from the
binary and need no site. `schema` and `check` read the files as they are at each
call, so an edit shows up without restarting the server. The same documentation
pages are also the server's resources, as `typedpress-docs:///<path>`.

`query` and the write tools run as the trusted command line, like `typedpress find`:
no access rules, drafts included. They are for a developer's own dev site:

- Without a flag, `query` reads this project's dev site and refuses any `site`.
  `typedpress mcp --allow-remote-read` lets it read another site, named as `--site`
  names one: a project directory, a deployment workspace or a WP-CLI `@alias`.
- The write tools are not listed without `--allow-writes`. With it, `run_action`,
  `insert` and `update` run `typedpress action`, `typedpress insert` and `typedpress update` on
  this project's dev site. They take no `site`, so they never reach another one.
- There is no delete tool.

A tool that runs a command (the compiler for `schema` and `check`, `typedpress find`
and the other site commands) stops it after 120 seconds, or the number of
seconds in `TP_MCP_TIMEOUT`, and stops it when the client cancels the request.

### Run the dev site from an agent

`typedpress dev` normally stays in the foreground until Ctrl+C, which an agent's
shell cannot do. Two things make it usable there:

- `typedpress dev --detach` returns once the site is up. The watcher keeps running
  in the background, rebuilds on save, and writes to `.tp/dev/dev.log`.
  `typedpress dev stop` stops it. When the first build fails it still starts
  WordPress and keeps watching, but prints the error and exits 1: the site
  does not serve the current source until a save builds.
- Without the flag, `typedpress dev` does the same by itself when its output is not a
  terminal and one of `CLAUDECODE`, `CODEX_SANDBOX`, `AI_AGENT` or `AGENT` is
  set to something other than empty, `0` or `false`. It says so on stderr. It
  never does this when `CI` is set, and `--foreground` turns it off.

`typedpress dev status --json` (and the `dev_status` tool) answers from
`.tp/dev/state.json`, which `typedpress dev` writes when the site is up:

```json
{"state":"running","url":"http://localhost:8787","port":8787,"admin":"http://localhost:8787/wp-admin/","site":"/work/my-app/.tp/dev/wordpress","watching":true,"pid":41822,"log":"/work/my-app/.tp/dev/dev.log","error":null,"wordpress":"7.1","php":"8.4"}
```

`state` is `none`, `stopped` or `running`, checked against the port itself.
`watching` is true while the recorded `typedpress dev` process exists; after
`--no-watch` it is false and `pid` is null. `error` is null while that
process's last build succeeded. After a build that failed it is
`{"message": …, "diagnostics": […]}`, with the compiler's diagnostics as
`typedpress check --json` reports them, and the site keeps serving the last
build that succeeded. `typedpress dev status` without `--json` still prints
Studio's own report.

The server speaks MCP revision 2026-07-28 (no handshake; `server/discover`) and,
for clients that open with `initialize`, 2025-11-25 and 2025-06-18.

## Use the running app: the site's MCP endpoint

Connect an agent to the same data and actions your frontend uses. TypedPress registers
them with WordPress's core Abilities API. The required MCP Adapter plugin exposes
them through an app-specific Streamable HTTP server.

### Find the endpoint and tools

For `defineConfig({ name: "subscriptions", ... })`, connect to:

```text
https://your-site.example/wp-json/mcp/typedpress-subscriptions
```

Keep any WordPress subdirectory before `/wp-json`. The app name and resource
names become kebab-case. A config named `myTracker` uses `typedpress-my-tracker`.

The runtime registers each enabled collection or table operation, and each
action, as an ability. The adapter replaces the slash in an ability name with a
hyphen in its MCP tool name:

| Config operation | Core ability | MCP tool |
|---|---|---|
| `subscriptions.list(...)` | `subscriptions/subscriptions-list` | `subscriptions-subscriptions-list` |
| `subscriptions.get(id)` | `subscriptions/subscriptions-get` | `subscriptions-subscriptions-get` |
| `subscriptions.create(data)` | `subscriptions/subscriptions-create` | `subscriptions-subscriptions-create` |
| `subscriptions.update(id, patch)` | `subscriptions/subscriptions-update` | `subscriptions-subscriptions-update` |
| `subscriptions.delete(id)` | `subscriptions/subscriptions-delete` | `subscriptions-subscriptions-delete` |
| `actions.monthlyBurn({})` | `subscriptions/monthly-burn` | `subscriptions-monthly-burn` |
| `actions.renewingSoon({ days: 3 })` | `subscriptions/renewing-soon` | `subscriptions-renewing-soon` |
| `actions.logCharge({ subscriptionId: 1 })` | `subscriptions/log-charge` | `subscriptions-log-charge` |
| `actions.cancel({ subscriptionId: 1 })` | `subscriptions/cancel` | `subscriptions-cancel` |

`charges` and `categories` have the same operation suffixes. List tools accept
filters, ordering, pagination, and declared relation loads. Update takes
`{ "id": 1, "patch": { "notes": "Review before renewal" } }`. List results
wrap rows in `{ "rows": [...] }`; action results have the handler's shape.
Always inspect `tools/list` for the actual input schema before calling a tool.

A `collection()` also has one tool per step of its [staged version](https://github.com/spacefast/zero/blob/main/docs/staged.md):
`<kind>-stage`, `<kind>-staged-get`, `<kind>-staged-compare`,
`<kind>-staged-promote`, `<kind>-staged-discard` and `<kind>-staged-preview`.
An agent can stage a change to a published item, read the comparison, and
leave the promote to a person, or to a credential that is allowed that tool.
`table()` kinds, such as the ones in this app, have none.

`api: { delete: false }` removes that operation. `agents: false` keeps the
underlying ability registered for PHP and WP-CLI, while hiding it from public
ability REST discovery and the app's MCP server. Globals also expose get and
update abilities. Jobs are exposed only when explicitly opted in with
`agents: true`; the subscriptions reminder is not an agent tool.

The app server lists named tools directly. The adapter's separate default
server has discovery and execution meta-tools; it is not the app endpoint above.
Both are built on `/wp-json` requests only: a request to TypedPress's own API
(`/__tp/api/v1`) never reaches `/mcp`, so it builds neither server and
registers no abilities it doesn't run.

The owning code is
[`Register.php`](https://github.com/spacefast/zero/blob/main/runtime/TypedPress/Wp/Abilities/Register.php), which calls
`wp_register_ability()` and the adapter's `create_server()`, and
[`Invoke.php`](https://github.com/spacefast/zero/blob/main/runtime/TypedPress/Wp/Abilities/Invoke.php), which routes execution
through the app pipeline. Input schemas come from
[`JsonSchema.php`](https://github.com/spacefast/zero/blob/main/runtime/TypedPress/Wp/Abilities/JsonSchema.php).
Abilities use the same access rules, field permissions, hooks, and transactions
as REST. An application password authenticates a WordPress user; it does not
bypass that user's access. In the subscriptions app, owner filters also apply
to MCP reads and writes. Trusted action handlers explicitly filter by owner.

### Who the agent is

The endpoint authenticates as core does. An agent connects as a WordPress user
with an application password, sent as HTTP Basic auth, and gets that user's
access and no more: the kinds' access rules, field permissions, hooks and
transactions apply to every tool call as they do on the API. An application
password is not the user's login password and not a TypedPress Identity browser token.

### Scoped agent credentials

`typedpress identity agent add <user> --name=<name>` creates an application password
for one agent. It is **read-only and has no access to personal data** until a
flag grants more:

| Flag | Grants |
|---|---|
| `--write` | creates, updates, deletes and abilities that aren't `readonly` |
| `--personal` | reading and setting email fields and fields with a read rule, and reading a user's own account details |
| `--abilities=blog/posts-list,blog/*` | only these abilities; no other route but the app's schema |

`typedpress identity agent list <user>`, `typedpress identity agent grant <user> <id>`
(with the same flags) and `typedpress identity agent revoke <user> <id>` manage them, and **Users → Profile →
Application Passwords** offers the same choices (*Allow writes*, *Allow personal
data*) and shows each password's scope.

A scope only narrows. The user's role, each kind's access rules and its field
rules still decide first, so a subscriber's credential with `--write` writes
what a subscriber may. It is enforced wherever the app can be reached: the
abilities run route, the MCP server, `/__tp/api/v1`, core's `/wp/v2` routes,
`/batch/v1` sub-requests, `?rest_route=` and method overrides. `GET
/__tp/api/v1` reports the scope of the credential asking, under
`runtime.credential`.

Whatever its grants and its user's role, a scoped credential can't do the
things that would remove its own limits:

- read or change application passwords, so it can't widen itself or mint another;
- change the account it signs in as: its password, email, login, roles or
  sign-in methods (TypedPress Identity's and Two Factor's routes). With `--write
  --personal` it can still edit the rest of the profile;
- administer the site: plugins and themes (deactivating TypedPress would switch the
  scope off), site settings, creating or promoting users, and any other plugin's
  route that asks one of those capabilities.

The last two hold on every way in: core's users route, TypedPress's API and the
abilities of an app's users kind.

An agent that has to do one of these needs an unscoped credential, which is a
choice its owner makes on purpose. A credential limited to named abilities also
sees only those in core's abilities list and in the MCP tool list. The list
covers what an action calls with `abilities.call` too: the inner ability runs as
the same credential, so it is named on the list beside the action, and a refusal
says which ability is missing.

A refusal is a 403 with the code `scope` (`tp_scope` on core routes; a tool
error over MCP) and says which grant is missing. Without `personal`, emails and
restricted fields are left out of every row, user and comment, and a filter,
sort or search on one is a 403 rather than a quiet probe.

Application passwords made before TypedPress's flows, and any created by other
clients or plugins outside TypedPress's flows, have no scope and work exactly as
WordPress ships them. A scoped password signs in only where its scope is
enforced: with the app plugin deactivated it is refused, never widened. The
refusal lives in the `typedpress-runtime` plugin, so removing that plugin (by
someone with file or WP-CLI access; a scoped credential can't) leaves a scoped
password an ordinary one. Revoke agent passwords before uninstalling TypedPress.

### Check an endpoint by hand

The endpoint is MCP over Streamable HTTP. `POST` an `initialize` request with
the `Authorization` header, `Content-Type: application/json` and
`Accept: application/json, text/event-stream`. Later requests repeat the
`Mcp-Session-Id` header the answer carried and send `MCP-Protocol-Version` with
the negotiated version. The repository's
[`mcp-proof.mjs`](https://github.com/spacefast/zero/blob/main/examples/subscriptions/scripts/mcp-proof.mjs) does exactly
that against any built TypedPress app (`TP_SITE`, `TP_APP`, `TP_TOOL`, and
`TP_APP_PASSWORD=user:application-password` in the environment), and prints
the `initialize` answer, the tool names and one tool call:


## Read pages as Markdown

While a TypedPress app is active, every public URL WordPress renders also has a
Markdown version at the same address plus `.md`:

| HTML URL | Markdown URL |
|---|---|
| `/hello-world/` | `/hello-world.md` |
| `/` | `/index.md` |
| `/category/news/?page=2` | `/category/news.md?page=2` |

- **Single posts and pages** show the title, then the stored content. Blocks
  Markdown can write come out as Markdown. Any other block comes out as the
  text, links and images of its rendered HTML. Raw HTML never comes through.
- **Archives, the blog index and search results** list each entry with a link
  to its own `.md` URL, plus links to the previous and next pages.
- **Only public content gets a Markdown URL.** Drafts, previews, private posts,
  feeds and TypedPress collections get a 404. A password-protected post shows only
  its title, even to a visitor who entered the password.
- **The `.md` URL is its own URL, the same for every visitor.** It is rendered
  as a signed-out visitor, even for a signed-in request. Page caches store it
  apart from the HTML.

Each HTML page links its Markdown version, so agents can find it:

```text
Link: <https://your-site.example/hello-world.md>; rel="alternate"; type="text/markdown"
<link rel="alternate" type="text/markdown" href="https://your-site.example/hello-world.md" />
```

On Spacefast, `Accept: text/markdown` on the HTML URL returns the same
Markdown. That response is never cached. Elsewhere, request the `.md` URL.

`/llms.txt` lists the site, then the newest 100 entries of each public post
type, and each public taxonomy's terms. Every entry links to its Markdown URL.

HTML pages, Markdown pages, `/llms.txt` and `robots.txt` send a
[Content-Signal](https://contentsignals.org/) of
`search=yes, ai-input=yes, ai-train=no`. To change it, filter
`tp_content_signal` in a plugin; return `''` to send none:

```php
add_filter('tp_content_signal', fn () => 'search=yes, ai-input=no, ai-train=no');
```
