Your server code is TypeScript. WordPress runs PHP. `typedpress build` compiles one into the other, once, on your machine. The compiler is written in Rust and runs only at build time. On the server there is no Node.js and no JavaScript engine: the app is PHP functions and a PHP runtime library.

## What gets compiled

The config is not compiled as a whole. It is evaluated, and the functions inside it are compiled:

| In `typedpress.config.ts` | Becomes |
| --- | --- |
| Tables, collections, fields, relations | Data in `tp/app/schema.php`, and SQL in `tp/_generated/migrations/` |
| Hooks (`beforeCreate`, `afterCreate`, …) | A PHP function per hook in `tp/app/functions.php` |
| `action()` and `job()` handlers, and `tp/app/**/route.ts` handlers | A PHP function per handler, in the same file |
| Access functions (`read: (ctx) => …`) | A PHP function per rule |
| Helpers they call, local or from npm | PHP functions in the same file |

## The steps

1. **Parse.** The compiler reads `typedpress.config.ts` and every module it imports, local files and installed npm packages, with the [OXC](https://oxc.rs) TypeScript parser. It never installs or runs a package.
2. **Lower.** It turns the syntax tree into its own intermediate form. A construct outside the supported subset fails here, with its location and what to write instead.
3. **Evaluate.** It runs the config as pure data: helpers, spreads, loops and factories work, but there is no I/O, no clock and no randomness, and a step budget stops runaway loops. Functions stored in the result are kept, not called.
4. **Extract.** It reads the schema out of the evaluated value, checks every config rule, and lists the functions that need PHP.
5. **Type-check and compile.** Each function is type-checked against the schema, so a hook knows its row's fields. It becomes native PHP wherever the types make that safe. Where JavaScript and PHP differ (truthiness, `+` on values of unknown type, string indexes, sort order) the PHP calls a helper on the runtime's `Js` class. Where neither is sound, the build fails.

The browser build of the same compiler runs in the [playground](/playground). It gives the same diagnostics as `typedpress check --json`.

The package must be installed (`npm ci`) before you build. Its source must use the same subset as your code. A package that uses something outside it fails the build at the line in the package that needs it. The compiler reads TypeScript, ES modules and static CommonJS. It erases a package's types, so your code can't name a type that only exists in a package.

## The PHP runtime

The compiled functions call a shared library, the `typedpress-runtime` plugin. Every app uses the same copy.

| JavaScript | PHP |
| --- | --- |
| `number` | `int` or `float` |
| `string` | `string`, stored as UTF-8. Indexes count UTF-16 code units, as in JavaScript |
| `boolean`, `null` | `bool`, `null` |
| `undefined` | A sentinel value, `JsUndefined::Value` |
| Arrays and plain objects | `JsArray` and `JsObject` handles, with identity: two variables can hold the same object |
| Functions | `Closure` |
| Classes | `JsObject` handles with a hidden class descriptor (`JsClass`) |
| `Promise`, `async`, generators | `JsPromise`, generators and a per-request job queue. `async` bodies run on PHP Fibers |
| `Map`, `Set`, `Date`, `RegExp`, `URL`, `BigInt` | `JsMap`, `JsSet`, epoch milliseconds, `RegExp`, `JsUrl`, `JsBigInt` |

`Js` holds the helpers where JavaScript and PHP give different answers: `Js::add` for `+`, `Js::truthy`, `Js::typeOf`, string slicing by UTF-16 index, and so on. Each must give the JavaScript result on the inputs its types allow. The compiler's contract tests run the generated PHP and compare it with Node.

## Where PHP differs from JavaScript

Two differences are known and tested. Everything else that compiles is meant to match Node. A difference that isn't listed is a bug.

- **`undefined` and `null`.** An explicit `undefined` keeps `typeof`, coercion and JSON omission. Some reads the compiler types statically as missing, and values typed only as `undefined` or `void`, become `null`. Imported JavaScript keeps a separate `undefined`.
- **Strings and surrogate pairs.** Strings index and slice by UTF-16 code unit, as in JavaScript. A result that would split a surrogate pair is refused at build time, or throws a `RangeError` at runtime, because UTF-8 can't store half a pair.

Code outside the subset fails the build. It never compiles into something that behaves differently. This config adds a number to a JSON field of unknown type:

The diagnostic is printed under the line, with a fix. The same message comes from `typedpress check`, `typedpress build` and the playground. Other refusals include:

- The clock or randomness while the config is evaluated. Use them in a handler, or `timestamp().defaultNow()`.
- `localeCompare`. Collation depends on the host, so the result wouldn't be repeatable. Use `<` and `>`.
- Packages that aren't installed, and Node built-ins. Handlers can use the global `fetch`, `process.env.NAME`, and part of `node:crypto` (`createHash`, `createHmac`, `randomBytes`, `randomUUID`, `timingSafeEqual`).
- Decorators, and computed class fields and methods. Use named classes with named fields and methods.

[Language support](/reference/language-support) lists every construct with a test behind it: what compiles, what differs, and what is refused, with the advice the compiler prints. [Diagnostics](/reference/diagnostics) lists the codes.
