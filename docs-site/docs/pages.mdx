Pages are optional. An app without a `pages/` folder builds and runs as before.

With pages, you write routes and layouts in TSX. `first-pages build` runs each one **once, at build time**, and writes Gutenberg block markup. WordPress renders that markup on every request, filling in the visitor's own data. This is not React. No React and no virtual DOM run on the server or in the browser. The only JavaScript a page sends is the module for each island, which runs on the WordPress Interactivity API.

[`examples/full-site`](https://github.com/spacefast/zero/tree/main/examples/full-site) is a complete site, and every file on this page comes from it.

## Files and routes

```text
full-site/
├── first.config.ts             collections, access rules, actions
├── pages/
│   ├── layout.tsx              wraps every page
│   ├── page.tsx                /
│   ├── not-found.tsx           the body of a 404
│   ├── about/page.tsx          /about
│   └── notes/
│       ├── page.tsx            /notes, a listing
│       ├── featured/page.tsx   /notes/featured, wins over [slug]
│       └── [slug]/page.tsx     /notes/<slug>, one note
├── components/NoteCard.tsx
├── islands/cheer.client.ts     the browser module of one island
└── styles/global.css
```

| File | What it does |
| --- | --- |
| `page.tsx` | A route. Only this name makes one |
| `layout.tsx` | Wraps every page below it, outermost first |
| `not-found.tsx` | At the root only: the body of a 404 |
| `(group)/` | Groups files without adding a URL segment |
| `[param]/` | One segment, last in the path. Needs `collectionPage()` |
| Anything else | A module the pages import. Never a route |

A static page next to an item route wins: `/notes/featured` is served by `featured/page.tsx`, and the collection refuses the slug `featured`. Paths WordPress owns, such as `/wp-admin` and `/wp-json`, can't be routes. Each static page is a hidden WordPress Page that First keeps in sync, so menus, SEO plugins and `get_permalink()` see a normal page. An item route serves the collection's existing posts.

## Data comes per request

A page runs once, at build time, when no request exists. So `item`, `params` and what `load()` returns are placeholders, filled in per request as the visitor:

| You write | It becomes |
| --- | --- |
| `{item.title}`, `href={note.href}`, `` `${item.title}!` `` | Escaped text or an attribute value |
| `rows.map((row) => …)` | A loop rendered on the server |
| `<Show when={v}>`, `<Show when={v} not>`, `<Show when={v} is="x">` | A condition decided on the server |
| `orElse(v, "fallback")` | `v ?? "fallback"`, decided per request |
| `<RichText value={item.body} />` | The item's stored body, through `the_content` |
| `link("/notes")` | That page's URL under the site's home URL |
| `content.query.<name>.findMany/findFirst(…)` | One query, run as the visitor |

Every query runs through the app's access rules with the visitor's account, like the REST API. An anonymous visitor never sees a draft or a staff-only field. A missing or unreadable item is a real 404 with the not-found page. Every response is sent with `Cache-Control: private, no-store`, because it depends on who is asking.

Code that would need the request at build time is refused, with the file, line and column:

| Refused | Code | Use instead |
| --- | --- | --- |
| `item.dek ? a : b`, `&&`, `\|\|`, `??`, `if`, `!` on request data | `dynamic_region` | `<Show>`, `orElse()` |
| `item.title + "!"`, comparisons, arithmetic | `dynamic_operator` | Template strings, `<Show is>` |
| `item.title.toUpperCase()` and other calls | `dynamic_call` | Render the stored value |
| A request value in `className`, `id`, `style`, `on*` or `data-wp-*` | `dynamic_attribute` | Branch with `<Show>` |
| `item.titel` | `unknown_field`, with a suggestion | The schema's field name |
| `import { db } from "first"` | `trusted_db` | `load({ content })` |
| `Date.now()`, `Math.random()`, browser globals, async components | `dynamic_call`, `browser_global`, `async_component` | `load()`, stored fields, an island |

## Metadata, CSS and assets

Export `metadata` or `generateMetadata(props)`, not both. They set `title`, `description`, `canonical` and `robots`. A layout's `title: { default, template }` applies once. First writes the only `<title>` and canonical link on its routes.

`import "./x.css"` adds a global stylesheet. `import styles from "./x.module.css"` gives a class map with names fixed at build time. Images and fonts a page imports become hashed files. Each route's CSS is enqueued before `wp_head`.

## Islands and the Interactivity API

An island is the only part of a page that runs in the browser. `<Island>` wraps plain HTML that uses `data-wp-*` directives. It names a store, a browser module, the app actions the module may call, and a starting context. This is the cheer button from the note page above:

<RepoFile path="examples/full-site/islands/cheer.client.ts" />

What happens to it:

1. **At build time**, the module is bundled for the browser with `@wordpress/interactivity` left out, because WordPress provides it.
2. **On the server**, the island's context is filled from the request (`noteId`, the current `count`). PHP runs `wp_interactivity_process_directives()` on the island, so the first paint already shows the right count.
3. **WordPress** registers the module as a script module that depends on `@wordpress/interactivity`. Through `wp_interactivity_config()` it gives the store each action's REST URL and a REST nonce. That is what `getConfig("fullsite/cheer")` reads.
4. **In the browser**, a click runs `actions.cheer`. It posts to the app's `cheer` action with the nonce, so a signed-in visitor calls it as themselves and an anonymous visitor as anonymous. The action's own access rule decides.

This is the bundle the build wrote for the store:

<PagesArtifact example="full-site" file="assets/island-" name="island bundle" />

Island children are escaped HTML. `on*` attributes, `style` and raw-text elements are refused. Two routes may share a store name only if they use the same module.

## Escaping

Request values never go through the block parser. After WordPress renders the blocks, PHP walks the HTML with WordPress's HTML API and fills each placeholder: text with `set_modifiable_text`, attributes with `set_attribute`, which applies `esc_url` to URL attributes. Only `http`, `https`, `mailto`, root-relative and fragment URLs are kept. A value can never become markup, a block delimiter or another placeholder.

## Build

```sh
first build site          # the backend, and the schema the pages are checked against
first-pages build site    # first/dist/wp-content/plugins/first-pages-<app>/
```

`first-pages build` exits `0` when it built, or when there is no `pages/`. It exits `1` with diagnostics, and `2` for a usage error. On an error it writes nothing, and the previous plugin stays. Install the `first-pages-<app>` plugin next to the app plugin.

The build also writes `first/pages.json`: every template, body and asset, the schema the pages were checked against, and a SHA-256 of each input. It holds no PHP. Commit it. When you publish to Spacefast, the host can't run your TSX, so it checks that `first/pages.json` matches your sources and refuses to publish when a page, layout, island or stylesheet changed after the last `first-pages build`.

## Not in this release

- React builds of the same components. Pages compile only to block markup today.
- Pages owned by content (`page.md`, `page.blocks.html`), and syncing them.
- Block themes (`theme.config.ts`). Layouts render inside the plugin's canvas.
- Post passwords on routed items. Such items are not served.
- Sitemaps of item routes, SEO plugin adapters, and redirects for moved routes.
- `first build` building pages. Run `first-pages build` after it.
- Full-page HTML caching. Routes skip shared caches.
- Arbitrary TSX or React behavior. Only the subset above compiles.
