Pages are optional. Without them, WordPress renders the site with its theme, and First is a backend.

A First app renders its own front end from `first/app/`: TSX that the compiler turns into PHP, rendered by WordPress on each request. It is one way, TSX to WordPress. The HTML matches what React would render for the same components, and no React runs on the server or in the browser.

## `first/app/`

```text
first/app/
├── layout.tsx                    wraps every page: export const metadata, default component
├── page.tsx                      /
├── not-found.tsx                 the 404 for URLs no route serves, and for notFound()
├── error.tsx                     a render error (logged; the page shows only this)
├── (site)/about/page.tsx         /about: a group adds no segment
├── colophon/page.md              /colophon: a WordPress Page an editor can change
├── notes/page.tsx                /notes?page=2, with export const search
├── notes/[slug]/page.tsx         /notes/<slug>: params.slug
├── docs/[[...path]]/page.tsx     /docs, /docs/a/b: params.path is a string[]
├── account/layout.tsx            export const guard = "subscriber"
├── api/notes/route.ts            export const access = "anyone"; export async function GET(req) { … }
└── _lib/                         never routed: colocated helpers
```

| Name | Meaning |
| --- | --- |
| `page.tsx` | A route. It may also export `POST`, `PUT`, `PATCH` or `DELETE` handlers for its URL, with `access` |
| `page.md` | A route whose content is a WordPress Page; see [Markdown pages](#markdown-pages) |
| `route.ts` | HTTP handlers only (`GET`, `POST`, …), for a URL with no page, with `access` or `signature` |
| `layout.tsx` | Wraps every page below it, outermost first. May export `guard` |
| `not-found.tsx` | At the root only |
| `error.tsx` | The nearest one above a page renders when the page throws |
| `[x]` / `[...x]` / `[[...x]]` | One segment / one or more / zero or more (last folder only) |
| `(group)` / `_private` | No URL segment / never routed |

Two files that serve one URL, a folder that shadows WordPress (`wp-admin`, `wp-json`, `feed`, …), a misspelled export (`metdata`) and a layout that wraps no page are build errors at the file, with the fix.

- Components are ordinary (async) functions. `&&`, `?:`, `??`, `.map`, `.length` and string methods work as in React.
- **Reads run as the visitor.** Every read a render makes is bound to the person viewing the page, so drafts, rows they may not read and masked fields never reach the HTML.
- `notFound()` renders `not-found.tsx` with a 404. `redirect(url, status?)` redirects (302 by default).
- `metadata` is an object or a function of the page's props: `title`, `description`, `canonical`, `robots: { index, follow }`. A layout's `title: { default, template }` wraps its pages' titles.
- `<Link href>` is an `<a>` that, once JavaScript runs, swaps only the router region (`@wordpress/interactivity-router`). `<Link prefetch>` prefetches on hover.
- `<Content value>` renders a post body through `the_content`. `<Html value>` places a literal as written and runs anything else through `wp_kses_post`.

### Markdown pages

<RepoFile path="tests/fixtures/app-router/first/app/(site)/guide/page.md" />

A `page.md` is a real WordPress Page. The file is its first version: the first request after a build stores the Markdown as blocks in a Page, with the front matter as its title, excerpt and status. From then on an editor changes it in wp-admin, in the block editor, and the route shows what they saved.

- It renders inside the `layout.tsx` files above it, and a layout's `guard` protects it, like a `page.tsx`. Its `<title>` and description come from the stored Page, so an editor's change to either shows.
- Front matter: `title`, `description`, `status` (`published` or `draft`), `canonical` and `robots: { index, follow }`. Without `title`, the first `# Heading` is the title. Any other key is a build error at its line: fields of your own belong to a kind with `sync`, where they have a type.
- A later version of the file replaces the Page only while nobody edited the Page on the site. An edited Page keeps the site's version, and the log names the file. Removing the file leaves the Page in WordPress; nothing is deleted. The exception is taking a page away from visitors: a file that newly says `status: draft`, or moves under a `guard`, unpublishes an edited Page too, and leaves its text alone.
- The route's path is the Page's address. WordPress's own address for it redirects there, and the editor's Preview button shows unsaved changes on the route.
- A draft is a 404 for visitors and shows to people who can edit it. A Page under a `guard` is stored private, so WordPress's REST API, search, sitemap and feeds never list it. A password set in wp-admin locks the body for every visitor.
- It has a Markdown twin at its URL plus `.md` and a line in `/llms.txt` when anyone may read it, and none otherwise.
- A `page.md` is one page with one URL, so it can't sit below `[slug]`. For many Markdown files, sync a folder into a kind and render it from a `page.tsx`.

A value a `search` field refuses (`?page=abc`) reads as absent. A `guard` is a role, `"authenticated"`, or `({ user }) => boolean`: a signed-out visitor goes to the login page, a signed-in one gets a 403.

Every HTTP handler says who may call it. `export const access` is `"anyone"`, `"authenticated"`, a role, a boolean or `({ user }) => boolean`, and the handler's reads run as the caller, like a page. `export const signature = { secret, header, scheme }` makes it a raw signed webhook: the body's HMAC is checked before the handler runs, and the handler runs as the system, so it can read what an anonymous visitor can't. A handler with neither, or with both, is a build error.

`first build` writes `first/_generated/routes.d.ts`. With it, `<Link href>` is checked against the app's routes and `PageProps<"notes/[slug]">` types `params`. Point TypeScript at First's JSX types:

```json
{ "compilerOptions": { "jsx": "react-jsx", "jsxImportSource": "first" } }
```

### Interactive components: `"use client"`

A component file under `first/components/` that starts with `"use client"` runs in the browser too. The compiler turns it into the WordPress Interactivity API: the server renders its HTML, and a small store module makes it interactive. There is no bundler and no Node at build time.

<RepoFile path="tests/fixtures/client-components/first/components/LikeButton.tsx" />

<RepoFile path="tests/fixtures/client-components/first/server.ts" />

- `useState(initial)` becomes a field of the element's `data-wp-context`. A setter takes a value or an updater.
- `onClick` and other event props become `data-wp-on--*` actions. An `await` in a handler is fine.
- Calling an `action()` the file imports posts to that action's endpoint with the REST nonce, so the caller is the visitor.
- `useEffect`, `useMount`, `useEvent` and `useRef` come from `"first/client"`, and `sharedState()` gives state every instance shares.
- npm imports, module-level helpers the browser doesn't have, and assigning state directly are build errors at the line, with the alternative.

The server HTML matches what React renders for the same component, which the parity tests check. These files come from [`tests/fixtures/client-components`](https://github.com/spacefast/zero/tree/main/tests/fixtures/client-components), which the test suite serves on WordPress and clicks in a browser.

### On WordPress

The router answers on `template_redirect`, before the theme. wp-admin, login, `/wp-json`, feeds, robots and First's own paths never reach it. When `first/app/` exists, a URL no route serves renders `not-found.tsx`. URLs WordPress itself resolves (a post, a category archive) keep the theme until a route serves them. Responses are `private, no-store` for now.

Without `first/app/`, nothing here loads and WordPress renders the whole site with its theme.

Every page also has a Markdown twin at the same URL plus `.md` (or with `Accept: text/markdown`), rendered as an anonymous visitor, and each HTML page links it. `/llms.txt` lists the app's pages that have no parameters and no guard. A page under a `guard` has no twin.

## The `pages/` pipeline (being replaced)

Until the cutover finishes, a root `pages/` folder still builds through the separate Node `first-pages build` described below, and `examples/full-site` uses it. `first/app/` replaces it; this pipeline and its helpers (`load()`, `<Show>`, `orElse()`, `<Island>`) go away in the same change set.

With `pages/`, `first-pages build` runs each route and layout **once, at build time**, and writes Gutenberg block markup. WordPress renders that markup on every request, filling in the visitor's own data. The only JavaScript a page sends is the module for each island, which runs on the WordPress Interactivity API.

[`examples/full-site`](https://github.com/spacefast/zero/tree/main/examples/full-site) is a complete site on this pipeline, and every file in this section comes from it.

### Files and routes

```text
full-site/
├── first.config.ts             collections, access rules, actions
├── pages/
│   ├── layout.tsx              wraps every page
│   ├── page.tsx                /
│   ├── not-found.tsx           the body of a 404
│   ├── about/page.tsx          /about
│   └── notes/
│       ├── page.tsx            /notes, a listing
│       ├── featured/page.tsx   /notes/featured, wins over [slug]
│       └── [slug]/page.tsx     /notes/<slug>, one note
├── components/NoteCard.tsx
├── islands/cheer.client.ts     the browser module of one island
└── styles/global.css
```

| File | What it does |
| --- | --- |
| `page.tsx` | A route. Only this name makes one |
| `layout.tsx` | Wraps every page below it, outermost first |
| `not-found.tsx` | At the root only: the body of a 404 |
| `(group)/` | Groups files without adding a URL segment |
| `[param]/` | One segment, last in the path. Needs `collectionPage()` |
| Anything else | A module the pages import. Never a route |

A static page next to an item route wins: `/notes/featured` is served by `featured/page.tsx`, and the collection refuses the slug `featured`. Paths WordPress owns, such as `/wp-admin` and `/wp-json`, can't be routes. Each static page is a hidden WordPress Page that First keeps in sync, so menus, SEO plugins and `get_permalink()` see a normal page. An item route serves the collection's existing posts.

### Data comes per request

A page runs once, at build time, when no request exists. So `item`, `params` and what `load()` returns are placeholders, filled in per request as the visitor:

| You write | It becomes |
| --- | --- |
| `{item.title}`, `href={note.href}`, `` `${item.title}!` `` | Escaped text or an attribute value |
| `rows.map((row) => …)` | A loop rendered on the server |
| `<Show when={v}>`, `<Show when={v} not>`, `<Show when={v} is="x">` | A condition decided on the server |
| `orElse(v, "fallback")` | `v ?? "fallback"`, decided per request |
| `<RichText value={item.body} />` | The item's stored body, through `the_content` |
| `link("/notes")` | That page's URL under the site's home URL |
| `content.query.<name>.findMany/findFirst(…)` | One query, run as the visitor |

Every query runs through the app's access rules with the visitor's account, like the REST API. An anonymous visitor never sees a draft or a staff-only field. A missing or unreadable item is a real 404 with the not-found page. Every response is sent with `Cache-Control: private, no-store`, because it depends on who is asking.

Code that would need the request at build time is refused, with the file, line and column:

| Refused | Code | Use instead |
| --- | --- | --- |
| `item.dek ? a : b`, `&&`, `\|\|`, `??`, `if`, `!` on request data | `dynamic_region` | `<Show>`, `orElse()` |
| `item.title + "!"`, comparisons, arithmetic | `dynamic_operator` | Template strings, `<Show is>` |
| `item.title.toUpperCase()` and other calls | `dynamic_call` | Render the stored value |
| A request value in `className`, `id`, `style`, `on*` or `data-wp-*` | `dynamic_attribute` | Branch with `<Show>` |
| `item.titel` | `unknown_field`, with a suggestion | The schema's field name |
| `import { db } from "first"` | `trusted_db` | `load({ content })` |
| `Date.now()`, `Math.random()`, browser globals, async components | `dynamic_call`, `browser_global`, `async_component` | `load()`, stored fields, an island |

### Metadata, CSS and assets

Export `metadata` or `generateMetadata(props)`, not both. They set `title`, `description`, `canonical` and `robots`. A layout's `title: { default, template }` applies once. First writes the only `<title>` and canonical link on its routes.

`import "./x.css"` adds a global stylesheet. `import styles from "./x.module.css"` gives a class map with names fixed at build time. Images and fonts a page imports become hashed files. Each route's CSS is enqueued before `wp_head`.

### Islands and the Interactivity API

An island is the only part of a page that runs in the browser. `<Island>` wraps plain HTML that uses `data-wp-*` directives. It names a store, a browser module, the app actions the module may call, and a starting context. This is the cheer button from the note page above:

<RepoFile path="examples/full-site/islands/cheer.client.ts" />

What happens to it:

1. **At build time**, the module is bundled for the browser with `@wordpress/interactivity` left out, because WordPress provides it.
2. **On the server**, the island's context is filled from the request (`noteId`, the current `count`). PHP runs `wp_interactivity_process_directives()` on the island, so the first paint already shows the right count.
3. **WordPress** registers the module as a script module that depends on `@wordpress/interactivity`. Through `wp_interactivity_config()` it gives the store each action's REST URL and a REST nonce. That is what `getConfig("fullsite/cheer")` reads.
4. **In the browser**, a click runs `actions.cheer`. It posts to the app's `cheer` action with the nonce, so a signed-in visitor calls it as themselves and an anonymous visitor as anonymous. The action's own access rule decides.

This is the bundle the build wrote for the store:

<PagesArtifact example="full-site" file="assets/island-" name="island bundle" />

Island children are escaped HTML. `on*` attributes, `style` and raw-text elements are refused. Two routes may share a store name only if they use the same module.

### Escaping

Request values never go through the block parser. After WordPress renders the blocks, PHP walks the HTML with WordPress's HTML API and fills each placeholder: text with `set_modifiable_text`, attributes with `set_attribute`, which applies `esc_url` to URL attributes. Only `http`, `https`, `mailto`, root-relative and fragment URLs are kept. A value can never become markup, a block delimiter or another placeholder.

### Build

```sh
first build site          # the backend, and the schema the pages are checked against
first-pages build site    # first/dist/wp-content/plugins/first-pages-<app>/
```

`first-pages build` exits `0` when it built, or when there is no `pages/`. It exits `1` with diagnostics, and `2` for a usage error. On an error it writes nothing, and the previous plugin stays. Install the `first-pages-<app>` plugin next to the app plugin.

The build also writes `first/pages.json`: every template, body and asset, the schema the pages were checked against, and a SHA-256 of each input. It holds no PHP. Commit it. When you publish to Spacefast, the host can't run your TSX, so it checks that `first/pages.json` matches your sources and refuses to publish when a page, layout, island or stylesheet changed after the last `first-pages build`.

### Not in this release

- React builds of the same components. Pages compile only to block markup today.
- Pages owned by content (`page.md`, `page.blocks.html`), and syncing them.
- Block themes (`theme.config.ts`). Layouts render inside the plugin's canvas.
- Post passwords on routed items. Such items are not served.
- Sitemaps of item routes, SEO plugin adapters, and redirects for moved routes.
- `first build` building pages. Run `first-pages build` after it.
- Full-page HTML caching. Routes skip shared caches.
- Arbitrary TSX or React behavior. Only the subset above compiles.
