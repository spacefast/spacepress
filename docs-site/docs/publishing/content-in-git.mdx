A kind with `sync` keeps its records as files in the repository (`content/<kind>/**/*.md` or `*.json`) and as posts or rows on the site. [`first sync`](https://github.com/spacefast/zero/blob/main/docs/config-api.md#sync) merges the two both ways, field by field. Run from a scheduler, it closes the loop between the people who edit in wp-admin and the people who edit in git:

- an edit saved on the site comes back to the repository as **one pull request**, which someone reviews and merges;
- a file change merged into the default branch goes to the site.

To set it up for a project on GitHub:

1. `first init --github`, commit the workflow it writes, and set `FIRST_SITE_URL` and `FIRST_APP_PASSWORD` in the repository's Actions settings ([the workflow](#the-github-workflow)).
2. On the site: `first git-dispatch set --repo=<owner/name>` and a token, so a save starts a run at once rather than at the next hourly one ([the site reports a save](#the-site-reports-a-save)).

## The pull request

```sh
FIRST_APP_PASSWORD=sync-bot:xxxx GITHUB_TOKEN=ghp_… first sync --pr --site https://docs.example.com
```

`--pr` runs the ordinary two-way sync, but not on the branch you have checked out. It fetches the default branch from `origin` into a temporary worktree and syncs there:

1. Files on the default branch that changed since the last sync go to the site, as `first sync` always does.
2. Records changed on the site are written to their files.
3. What differs from the default branch is pushed to a branch named `first-sync/<site host>[/<site path>]/<time>`, and a pull request is opened from it into the default branch. Its description lists the files it writes or deletes (the first 200).

Running it again is safe:

| The site and the default branch… | `--pr` |
|---|---|
| agree | does nothing; an open sync pull request is closed with a comment, since there is nothing left in it |
| differ in the same way the open sync pull request already carries | does nothing |
| differ, and a sync pull request is open | adds one commit to its branch (a merge of the default branch and the new tree, so the push never rewrites history) and updates its description |
| differ, and none is open | opens one |
| differ only in `.first/sync-base.json` (a file change reached the site and nothing came back), and no sync pull request is open | pushes that commit to the target branch as a fast-forward; if the branch is protected or moved, it opens a pull request instead |

There is one sync pull request per site. Edit content on the default branch or on the site, not on the sync branch: a commit there that `first sync` didn't make stops later runs, which say which commit it is, until the pull request is merged or closed. Merges, such as GitHub's *Update branch*, are fine.

The checkout you run `--pr` from is never committed on or changed.

`--repo owner/name` and `--base branch` choose the repository and the target branch. By default they are `GITHUB_REPOSITORY` (or `origin`'s GitHub URL) and the repository's default branch; `origin` must be that repository. `GITHUB_API_URL` points at GitHub Enterprise. The pull request, its description and comments go through GitHub's REST API with `GITHUB_TOKEN`; the command doesn't need the `gh` CLI. The branches are pushed with `git push origin`, so git needs credentials for `origin` too: in GitHub Actions, `actions/checkout` leaves the workflow's token for it; elsewhere, use a credential helper or an `origin` URL git can push to.

`--pr` syncs every synced kind (it takes no `--only`), since the pull request is rebuilt from all of them. Synced folders must not be ignored by git: a file the sync writes there can't go in the pull request, and the run stops instead.

## The GitHub workflow

```sh
first init --github
```

writes `.github/workflows/first-sync.yml` at the root of the repository. It runs `first sync --pr` from the project's own `first` package (`npx --no-install first`), on:

| Event | What it does |
|---|---|
| `schedule`, hourly | brings the site's edits back as the sync pull request |
| `repository_dispatch` of type `first-content-changed` | the same, as soon as the site reports a saved record ([below](#the-site-reports-a-save)) |
| `push` to the default branch that changes a file below a synced folder | sends those files to the site; site edits made meanwhile come back as the pull request |
| `workflow_dispatch` | a run by hand, from the Actions tab |

Its `paths` are the folders your kinds sync (only branch pushes count; tags start no run). When they change, `first check` says the workflow is out of date and `first init` writes it again. Its first line names the project it was written for: a repository has one sync workflow, so another project in the same repository leaves it alone, and its `first init --github` refuses rather than replace it. Delete that line to make the file yours; `first init` then leaves it alone too. `--github` needs the project in a git repository, since the file goes at the repository's root.

It names its settings and never holds a value. Set them under **Settings → Secrets and variables → Actions**:

| Name | Kind | Value |
|---|---|---|
| `FIRST_SITE_URL` | variable | the site's URL |
| `FIRST_APP_PASSWORD` | secret | `user:application-password` for sync ([permissions](#permissions)); or `FIRST_TOKEN` |

The workflow grants its own `GITHUB_TOKEN` `contents: write` and `pull-requests: write`. In **Settings → Actions → General**, *Allow GitHub Actions to create and approve pull requests* must be on for it to open the pull request. Runs never overlap (`concurrency: first-sync`): a run waits for the one in progress, and a newer waiting run replaces an older one, which loses nothing because each run syncs the latest state. The actions it uses are pinned by commit.

## The site reports a save

Without it, the site's edits wait for the hourly run. With it, the site tells the repository when an editor saves a synced record, and the workflow runs at once:

```sh
first git-dispatch set --repo=acme/docs              # the repository to tell
printf %s "$TOKEN" | first git-dispatch set --token  # where WordPress can keep it (below)
first git-dispatch status
```

- A save of a record of a synced kind, in wp-admin, through the API or by any other plugin, queues one `repository_dispatch` of type `first-content-changed`. It is sent a minute later; saves in that minute join it, so an editing session sends one request, not one per save. Saves of other kinds send nothing, and neither do the writes `first sync` makes itself.
- It is a First background job, run by Action Scheduler like every other First job, retried with backoff when GitHub doesn't answer 2xx. **Tools → Scheduled Actions** shows it; `first jobs list` too.
- The token needs `contents: write` on the repository (a fine-grained token limited to it is enough). It is read from `FIRST_GITHUB_DISPATCH_TOKEN` (the environment or a `wp-config.php` constant). Otherwise it is read from WordPress's Secrets API (WordPress 7.2), where `set --token` stores it, encrypted. Where WordPress has no Secrets API, `set --token` refuses: the token is never stored in the database in clear text, so set it in the environment.
- `FIRST_GITHUB_REPOSITORY` in the environment overrides the stored repository, `FIRST_GITHUB_DISPATCH_WINDOW` changes the minute (in seconds), and `FIRST_GITHUB_API_URL` points at GitHub Enterprise.

## Conflicts

When the same field of the same record changed in git and on the site since they last agreed, `first sync` writes neither side. It writes `.first/conflicts/<uid>.md` with both versions and the version they started from, between git's conflict markers.

With `--pr`, the conflict files are committed to the sync pull request, the description counts them, and a comment lists them each time the set of conflicts changes. Nothing is resolved for you: the conflict file shows both versions, and you make the record the same on both sides.

1. Pick the version to keep from the conflict file.
2. Edit the record on the site into it, or edit its file on the default branch into it (or both).
3. The next `first sync --pr` finds the two sides equal, records that in the sync base, and drops the conflict file from the pull request.

`first sync resolve <uid>` is for a checkout you sync with plain `first sync`; the sync base it writes is local to that checkout, so with `--pr` use the steps above.

## Permissions

| Credential | Needs |
|---|---|
| `FIRST_APP_PASSWORD` (or `FIRST_TOKEN`) | A user whose role may read and update the synced kinds. Create an application password for sync alone: `first identity agent add <user> --name=sync --write`. A [scoped agent credential](https://github.com/spacefast/zero/blob/main/docs/agents.md#scoped-agent-credentials) is read-only unless given `--write`; read-only, the run pulls site edits into the pull request, but every file change it would push to the site is refused (exit 4) and nothing is pushed to GitHub. Fields a user may not read are left out of the files, never cleared. |
| `FIRST_GITHUB_DISPATCH_TOKEN` (on the site) | `contents: write` on the repository, which is what GitHub asks for a `repository_dispatch`. It can't open pull requests or read anything else when it is a fine-grained token for that one repository. |
| `GITHUB_TOKEN` | `pull-requests: write` (open, update, comment, close) and `contents: write` (delete a branch it pushed when GitHub refused its pull request) on the repository. The pushes need `contents: write` for git's own credentials. In GitHub Actions the workflow's own token is both, once the workflow's `permissions` grant them. |

Pull requests opened with a workflow's own `GITHUB_TOKEN` don't start other workflows, so checks that run on `pull_request` don't run on the sync pull request. Use a fine-grained token or a GitHub App's token in its place if they must.
