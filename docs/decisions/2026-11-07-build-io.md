# Build only what changed in wp-content

`zero check` on `examples/blog` takes 7 ms; `zero build` took 14-35 s. Compiling is
negligible. Almost all of the time went to processes and file copies:

- `php -l` ran once per PHP file: 159 processes per blog build, 128 of them for
  the embedded `zero-runtime`, which is identical for every build of a given binary.
- Every build copied the whole previous output into a staging tree, re-extracted
  every dependency archive, copied each extracted tree into the stage, rewrote the
  embedded runtime, identity and admin trees (about 34 MB) and re-zipped them,
  then deleted the previous output file by file.

## Decision

**Lint what the build generates, in one process.** A user build lints only PHP it
produced from user input: the substituted plugin headers, `schema.php`,
`functions.php`, and PHP under the project's `public/`. All of them go to one
`php -l f1 f2 …` call. PHP before 8.3 lints only the first argument, so any file the
batch did not confirm is linted on its own; nothing is skipped silently. The embedded
runtime, identity and admin PHP is constant per binary, so Zero's own `cargo test`
lints it (a unit test in `src/commands/build.rs` writes every embedded PHP file
outside `vendor-prefixed` and runs the same lint), and CI's `rust` job runs it.

**Keep plugin trees that already match.** The stage starts empty. For each plugin:

- A generated plugin is built in memory first. If the previous output holds exactly
  that tree (same paths, same bytes, nothing extra) and its `.zip`, both are kept.
  Otherwise the tree is written, linted and zipped.
- A dependency is kept when the previous output's `zero-manifest.json` was written
  by this Zero version and records the same slug, version, source, archive sha256
  and tree digest, and the installed tree still hashes to that digest. Otherwise its
  archive is extracted straight into the stage. The collision rules are unchanged: a
  case-colliding name, or an existing directory that the lock does not own or whose
  digest differs from the lock, still fails the build before anything is published.

**Publish by renaming.** Everything the build did not replace (kept plugins, the
user's own plugins, other top-level entries) moves from the previous output into
the stage by `rename`, then the stage is renamed into place and the lock is
persisted. Any failure in that sequence moves every entry back and restores the
previous output. All checks, lints and zips run before the first rename, so a
rejected build still leaves the previous output and lock untouched. The commit is
now a few same-filesystem renames instead of two; a crash inside that window needs
the same manual recovery from the temporary directory as before.

**Zip lazily.** Nothing in this repository reads the `.zip` files: deployment
(`runtime/Zero/Deployment`), `zero dev` (`scripts/dev/studio.mjs`) and the system
tests copy plugin directories. They exist for people who upload plugins by hand
(README "Anywhere else"). They stay, but a zip is written only when its plugin was
rewritten, so a no-change rebuild zips nothing.

## Alternatives

- Directory `clonefile(2)` of the whole output into the stage costs about 0.1 s on
  APFS and would keep a single-rename commit, but it is macOS-only and still leaves
  the full previous tree to delete afterwards. Hard-link trees cost about as much as
  copying (1.5-2.7 s for 5,000 files here).
- Dropping the zips, or putting them behind a flag, changes the documented artifact
  for little gain once unchanged plugins are not re-zipped.
- Caching extracted dependency trees per archive would also skip extraction on a
  fresh output, at the cost of a second cache keyed by patch revision. Not needed:
  extraction now runs only when a dependency changes or the output is new.
