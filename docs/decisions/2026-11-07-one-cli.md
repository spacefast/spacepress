# One CLI: `zero` builds, WP-CLI runs the site

Date: 2026-11-07. Status: accepted.

## Problem

Zero had five ways to reach a site, with overlapping jobs and flags:

- `zero dev wp [dir] -- <args>`: WP-CLI on the Studio dev site.
- `zero deploy wp --workspace <dir> -- <args>`: WP-CLI on an offline workspace.
- `zero migrate site <file> --wp "<wp-cli command>"`: a Rust wrapper that piped a file into
  `wp zero migrate-legacy -`, with its own way to name the target.
- `zero sync --site <url> --app-password <user:pass> | --bearer <jwt>` and
  `zero doctor --site <url> --token <t>`: credentials as flag values.
- `wp zero …` and a separate `wp zero-identity …` namespace.

An author had to learn which of these applied, and help text lived in four places (`src/cli.rs`,
`App::USAGE`, `packages/cli/bin/zero.mjs`, the docs).

## Rule

1. **`zero` is the only CLI an author learns.** Commands that work on the project's files are
   native Rust: `build`, `check`, `dev`, `doctor`, `migrate app|config`, `deploy`, and `sync`.
2. **Every site operation is implemented once, in the `zero-runtime` plugin, as `wp zero <cmd>`.**
   That covers `migrate`, `seed`, `jobs`, `run`, `abilities`, `action`, `find`, `insert`, `update`,
   `delete`, `publish-due`, the `migrate-legacy*` importers and `identity`. No site logic lives in
   Rust.
3. **`zero <site cmd> …` forwards to `wp zero <site cmd> …`**, byte for byte: arguments, stdin,
   stdout, stderr and exit status. `zero wp <args>` forwards any WP-CLI command, so `zero wp plugin
   list` is the shortcut for what WordPress already does.
4. **One flag picks the site: `--site`.**
   - absent: the dev site (`zero dev`'s Studio site) of the project in the current directory;
   - a directory: that project's dev site, or, when the directory is an offline deployment
     workspace, that workspace (through the deploy adapter, whose receipts keep native output in a
     private file);
   - `@alias`: a WP-CLI alias from `wp-cli.yml`, run with the `wp` on `PATH`
     (`wp @prod zero jobs list`). Remote access, SSH and containers are WP-CLI's job;
   - an `http(s)://` URL: only for the two commands that speak HTTP, `sync` and `doctor`.
5. **Credentials come from the environment, never a flag value:** `ZERO_APP_PASSWORD`
   (`user:application-password`) or `ZERO_TOKEN` (a bearer token), read by `sync` and `doctor`.
6. **One command table** (`runtime/Zero/Cli/commands.json`) lists every command with its group,
   arguments and summary. `zero help` prints it grouped as "build" and "site"; `zero` uses it to
   decide what to forward; `wp zero` (no arguments or `help`) prints the site group from the same
   file, which ships inside the runtime plugin. Adding a site command means one table row and one
   PHP handler.

## Decisions and why

- **`zero sync` stays in Rust.** It reads and writes the project's files, keeps merge bases under
  `.zero/`, writes conflict files and makes a git commit. Those are local file operations;
  the server already owns body conversion and merges (`/sync/{c}/convert`, `/merge`). Moving it into
  WP-CLI would need WordPress to reach the author's working tree, which is wrong for a deployed
  site. Only its site selection (`--site`, dev site by default) and credentials (environment) change.
- **`zero doctor` stays in Rust.** It checks the built artifact on disk, and optionally a site over
  HTTP the way a visitor sees it. `--token` goes; `ZERO_TOKEN` replaces it.
- **`wp zero identity`, not `wp zero users`.** The identity commands cover OIDC applications,
  signing keys and webhooks as well as accounts, and `users` reads too close to core `wp user`.
  Identity commands print the same `{"data": …}` / `{"error": …}` JSON as every other `wp zero`
  command. The identity plugin registers its handler through the runtime's dispatcher, so it runs
  without an app transaction, as before.
- **`zero migrate site` is deleted.** `zero migrate-legacy - < content-model.php` reaches the same
  PHP command through the forwarder (stdin is passed through), and `--site` replaces `--wp`.
- **`zero dev wp` and `zero deploy wp` are deleted** in favour of `zero wp [--site …]`.
  `zero publish|backup|restore` move under `zero deploy`, which keeps its offline-adapter options.
- **`--site` values that look like names need `@`.** A bare word is a directory; an alias is
  always `@name`, as in WP-CLI. No guessing between the two.
- **Unknown commands are refused locally** with the help text, instead of being sent to WP-CLI,
  so a typo doesn't start Studio or open an SSH connection.
- **No aliases or deprecation shims.** Zero has no users yet.

## Before and after

| Before | After |
| --- | --- |
| `zero dev wp [dir] -- plugin list` | `zero wp plugin list` (`--site <dir>` for another project) |
| `zero dev wp [dir] -- zero jobs list` | `zero jobs list` |
| `zero deploy wp --workspace <w> -- post list` | `zero wp --site <w> post list` |
| `zero migrate site m.php --wp "wp --path=/srv"` | `zero migrate-legacy - --site @srv < m.php` |
| `zero sync --site <url> --app-password u:p` | `ZERO_APP_PASSWORD=u:p zero sync --site <url>` |
| `zero sync --site <url> --bearer <jwt>` | `ZERO_TOKEN=<jwt> zero sync --site <url>` |
| `zero doctor --site <url> --token <t>` | `ZERO_TOKEN=<t> zero doctor --site <url>` |
| `zero publish …`, `zero backup …`, `zero restore …` | `zero deploy publish …`, `zero deploy backup …`, `zero deploy restore …` |
| `wp zero-identity suspend 7` | `wp zero identity suspend 7` (or `zero identity suspend 7`) |
| `wp zero-identity app add --name=…` | `wp zero identity app add --name=…` |

## Testing

Behaviour only: the `zero` binary runs against fixtures, and one lane serves a real WordPress
(WP-on-SQLite from `tests/php/wp.php`) and checks that `zero <site cmd> --site @alias` prints the
same JSON as `wp @alias zero <site cmd>`. Tests for removed commands and flags are deleted, not
inverted.
