# TSX compiles to PHP in the Rust compiler, through a component IR

Date: 2026-11-08. Status: accepted. Spec: [tsx-to-php.md](../spec/tsx-to-php.md),
[rendering.md](../spec/rendering.md) §2–§4, [build-plan.md](../spec/build-plan.md) §5.

## Problem

Pages today are a separate Node package (`packages/pages`). A page runs once at
build time with request data as placeholder proxies (`symbolic.ts`), and
`runtime/pages/Renderer.php` fills the placeholders per request
([2026-11-04](2026-11-04-pages-placeholders-and-plugin.md)). A proxy only
records reads. It can't express `{n && <b/>}`, `a ? <X/> : <Y/>`, `.length`, or a
method call on request data, so every one of those needs a helper (`<Show>`,
`orElse()`, `count()`). The spec wants plain React-style TSX: async server
components that read data and branch on it, and `"use client"` components
that become interactive in the browser. Hosting boxes have no JavaScript at
request time.

Meanwhile the Rust compiler already lowers a typed TypeScript subset to PHP
with JavaScript semantics (`src/lower.rs`, `src/compile.rs`,
`runtime/Zero/Js*.php`), checked against Node by `tests/differential/`. It
refuses JSX at `src/lower.rs` (`E::JSXElement`, `E::JSXFragment`) and at
`src/loader.rs` ("JSX files can't be part of a Zero config").

## Decision

**JSX → component IR → PHP, in the Rust compiler.** Expression lowering needs
the types the compiler already has, and per-request rendering must be PHP.
Node runs only in tests, never in a build: React renders the Node half of the
HTML parity tests. Block output from a page (`packages/blocks`) needs Node to
serialize, so it stays out of this workstream until it has a Node-free path.

**Hosted builds have no Node.** `sf publish` → `compile-sources` and the wasm
capture compile with the Rust compiler alone (`docs/pages.md`: a box compiles
without Node, and the wasm build excludes `oxc_transformer`). So everything a
page serves comes out of the Rust compiler:

- PHP for every component, from generator A;
- the `"use client"` store modules as plain JavaScript, from generator B. The
  first slice refuses non-relative imports in `"use client"` files, so there is
  nothing to bundle; npm packages in client code need a later decision;
- CSS: plain `.css` imports are copied as assets, and CSS modules are rewritten
  by the compiler (class names hashed from the file path, as `packages/pages`
  does today);
- other imported files (images, SVG) are copied with content-hashed names;
- one manifest listing routes, islands and assets, in the shape
  `runtime/pages/Plugin.php` reads today (`version`, `routes`, `islands`,
  `notFound`), written by the compiler instead of `zero-pages build`.

Everything new runs in the v2 app plugin's request path, so nothing changes
for a Space that isn't serving v2. Existing 0.8 apps keep running as 0.8 until
their owner runs `zero migrate app --from zero-0.8`, and that converter always
emits code for the current v2 surface.

### Where JSX is admitted

JSX parses only in `.tsx` files that are under a `components/`, `pages/` or
`app/` folder, or that start with `"use client"`. The compiler discovers
server components under the Zero root, `zero/components/`, and route files
under `pages/` until workstream 6 renames routing to `zero/app/`. The renderer
takes a component and its props and knows nothing about routing, so that
rename only changes discovery.

A module that `zero.config.ts` imports still can't contain JSX: the config is
evaluated at build time and JSX never runs there, so the evaluator refuses it
wherever it appears, including in a `"use client"` file.

### The IR

Lowering a component produces a tree of nodes:

| Node | Holds |
|---|---|
| `Element` | tag, attributes (each a static string or an expression), children |
| `Fragment` | children |
| `Expr` | one `{…}` expression container, lowered by the existing expression lowering |
| `Component` | the callee (a compiled component), props (expressions), children |
| `Text` | literal text, with JSX whitespace rules already applied |

Every node keeps its source span and an escaping context: text, attribute
value, URL attribute, or (only through `<Html>`/`<Content>`) trusted HTML.
Expression nodes also record provenance: literal, prop, query result, or
derived. Interactivity output uses provenance to decide what becomes context
and what becomes a getter. Static subtrees fold to literal strings at compile
time.

JSX inside an ordinary expression (`cond && <b/>`, `list.map((x) => <li/>)`,
`a ? <X/> : <Y/>`) is an ordinary value of type `Zero\Html`. That is why `&&`,
`?:`, `??`, `.map`, `.length` and method calls on request data need nothing
JSX-specific: they are the same expressions the compiler lowers for handlers.

### Code generator A: PHP that writes escaped HTML

Each component compiles to one PHP function in the app's namespace, named from
its module path and export (`component__<path>__<Name>`), so two modules can
export the same name. It takes the props object and returns a `\Zero\Html`
value, markup the renderer has already escaped. `Html` is not a string to
JavaScript code: interpolating it (`${<b/>}`) prints `[object Object]`, as in
React. An element renders as concatenation. A static run becomes one
literal, and a child goes through one helper, `\Zero\Html::child($value)`,
which follows React 19's rules:

- `null`, `undefined`, `true` and `false` render nothing;
- `0` renders `"0"`, and numbers print as JavaScript prints them (`Js::str`:
  `NaN`, `-0` → `0`, `1e21` → `1e+21`);
- a string is escaped as text;
- a `\Zero\Html` value is placed as it is;
- arrays and nested arrays concatenate;
- an object that isn't `Html` is a build error where the type is known, and a
  render error otherwise (React throws "Objects are not valid as a React child").

Escaping spells entities the way `react-dom/server` does, so parity compares
bytes: `&amp;`, `&lt;`, `&gt;`, `&quot;`, and `&#x27;` for `'`, in text and in
attribute values. Attributes follow `react-dom-server`'s own property table,
ported as data and pinned to the React version the parity tests run (19.2.8).
The table covers names React rewrites (`tabIndex` → `tabindex`, the SVG
aliases such as `strokeWidth` → `stroke-width`) and names it keeps in
camelCase (`readOnly`, `autoComplete`), which values it drops, and per-tag
rules such as `<input>` writing `checked` and `value` last. Some of the rules:

- `className` → `class` and `htmlFor` → `for`; `class` and `for` written
  as-is are accepted too, since converted 0.8 pages use them;
- a boolean attribute that is `true` prints `name=""`, and one that is
  `false`, `null` or `undefined` is omitted;
- `aria-*` and `data-*` print `true`/`false` as strings;
- void tags close as `<br/>`;
- `style` objects print as `color:red;font-size:12px` (React's own rules for
  units and hyphens), and only with compile-time keys.

URL attributes (`href`, `src`, `action`, `formAction`, `xlinkHref`) allow only
the schemes `Renderer.php` allows: http(s) and mailto. A URL without a scheme
(nothing that looks like `scheme:` before its first `/`, `?` or `#`) is also
allowed, so relative links like `?page=2` and `posts/1` work. A
protocol-relative `//host` is refused. A literal URL that fails is a build
error, and a computed one drops the attribute at render time. The value is
escaped with React's entity table, not `esc_url`, so `&` prints `&amp;` as in
React. React instead rewrites `javascript:` URLs, so parity fixtures use safe
URLs, and the unsafe case is tested on the PHP side alone.

**Children and deferred rendering.** As in React, building an element
evaluates its props and child expressions, but a component's body runs only
when its element is placed in output that is itself rendered. Children a
component never places never run, so their queries, errors and reads (which
feed the cache purge index, rendering.md §6.2) never happen, and children
placed twice render twice. A component with no children receives `children`
as `undefined`, so `children && …` behaves as in React. A component can place
`children` or pass it on to another component, but it can't inspect it.
`Children.map`, `cloneElement` and reading `props.children` as data are
refused.

**Async server components.** `await` inside a server component lowers to a
blocking call, as it already does in authored handlers
([2026-11-07](2026-11-07-promises-generators-streams.md), "authored
TypeScript"). The compiled function returns once its data is in, and a parent
calls children in source order. There is no Suspense and no streaming; both
are refused, with the subset's alternative named.

**Raw HTML** enters only through two components:

- `<Content value>` renders a post body through `the_content`, as `<RichText>`
  does today;
- `<Html value>` places a literal or build-time string as it is, and runs any
  other value (request data, query results) through `wp_kses_post` first. The
  IR's provenance decides which.

`dangerouslySetInnerHTML` is refused and the error names `<Html>`. Neither
component exists in the first server slice; until they land, the refusal says
raw HTML isn't supported yet.

### Code generator B: Interactivity API output for `"use client"`

A `"use client"` component compiles to three outputs, following the mapping
table in rendering.md §4.1. A component's store namespace is
`<app>/<Component>`, using the app's slug, so it never collides with Zero's
own built-in components (`zero/Comments`, `zero/Search`). Two client
components with the same name in one app are a build error that names both
files.

1. **Server HTML (PHP), from generator A.** A client component must return
   exactly one intrinsic element. A fragment, a component or a conditional at
   the root is a build error that says to wrap it in an element. That root
   element gets
   `data-wp-interactive` and `data-wp-context` with the `useState` initial
   values and serializable props. Dynamic text gets `data-wp-text`, dynamic
   attributes get `data-wp-bind--*`, and handlers get `data-wp-on--*`.
   `{cond && <el/>}` gets `data-wp-bind--hidden` on `el` only when all of
   these hold: `cond` is typed `boolean`, `el` is one intrinsic element, and
   nothing inside `el` relies on `cond` to narrow a type (so it renders safely
   while hidden). Anything else, including `a ? <X/> : <Y/>`, is refused until
   workstream 7's `<template>` output. When dynamic text shares its parent
   with other children, the compiler wraps it in a `<span>` that carries only
   `data-wp-text`.

   **Generator A prints every value; WordPress's directive pass does not run
   on compiled islands.** `wp_interactivity_process_directives` re-renders
   `data-wp-text` and `data-wp-bind` with its own escaping and number
   formatting (`esc_html` prints `'` as `&#039;`, PHP rounds `0.1 + 0.2` to
   `0.3`, a bound boolean prints `hidden`, not `hidden=""`), so running it
   would change bytes the parity tests check. Compiled islands therefore skip
   it. This departs from rendering.md §4.1, which has PHP closures compute the
   first render; generator A already does that with JavaScript's own number
   formatting.
2. **A store module (JS).** The compiler writes its TypeScript source:
   - `state` getters for derived `const`s, with the author's expressions kept
     verbatim and only references rewritten (`count` → `getContext().count`);
   - actions for handlers, where an async handler becomes a generator and each
     `await` becomes a `yield`; a handler that calls `preventDefault`,
     `stopPropagation` or reads `currentTarget` is wrapped in `withSyncEvent`;
   - server action calls as `fetch` to the action endpoint, with the REST nonce
     from `getConfig()`.

   The compiler writes this module as plain JavaScript, with no bundler. It is
   registered as a script module that depends on `@wordpress/interactivity`,
   and enqueued only on routes that render the component.
3. **No PHP closures for derived state.** Because WordPress's directive pass
   doesn't run on compiled islands (step 1), nothing reads
   `wp_interactivity_state` closures, and the client computes derived values
   from context with the step 2 getters.

The first Interactivity slice covers `useState`, derived values, text,
attribute and boolean-hidden bindings, event handlers and server-action calls.
That is what a counter and the spec's `LikeButton` need. Lists
(`data-wp-each`), `<template>` toggling, `useEffect`, `useRef`, `sharedState`
and the built-in components belong to workstream 7. Until they land, they are
refused with a message naming them.

The client half of action calls uses the endpoint the pages plugin uses today,
`rest_url('zero/v1/actions/<name>')`, and moves when workstream 2's
`/__zero/api/v1` facade lands. It never uses the paths Zero 0.8 used
(`/__zero/config`, `/__zero/run`, `/__zero/auth/*`, `/__zero/realtime/events`).

### Parity tests

The Node half renders each fixture with React 19.2.8, pinned in
`tests/differential/html/package.json`. It uses `react-dom/static`
`prerender`, which accepts async components; build-plan §5 names
`renderToStaticMarkup`, but that throws on async components ("A component
suspended while responding to synchronous input"), so build-plan §5 should
say `prerender`. The PHP half runs the compiled functions under PHP with the
runtime's bootstrap, as `tests/differential/run-php.php` already does for
handlers. Both get the same props from JSON. The comparison normalizes
exactly these things:

- React's `<!-- -->` text separators are removed;
- the `<link rel="preload" as="image" …/>` React emits ahead of an `<img>`
  without `loading="lazy"` is removed (a page head concern);
- `<title>`, `<meta>`, `<link>`, `<script>`, `<style>` and `<base>`, which
  React hoists into the head, are refused in components, and the root
  layout's `<html>` (where React adds `<!DOCTYPE html>`) is compared once the
  layout slice lands, with the doctype written by the page shell;
- in client components, `data-wp-*` attributes are removed,
  compiler-inserted `data-wp-text` spans are unwrapped, and elements the
  compiler kept with `hidden` for a false condition are removed (React leaves
  them out).

Entity spelling, attribute order, boolean attributes and whitespace are compared
as they are. The cases extend `tests/differential/` and the parity test in
`tests/compiler.rs`. The browser half extends the existing hosted-pages lane,
`tests/wp/hosted-pages-run.sh`: it loads a page with a `"use client"` counter
with `SCRIPT_DEBUG` on (WordPress serves the unminified Interactivity runtime,
which is the only build that logs warnings), checks that hydration makes no
DOM mutations (a `MutationObserver` registered before the store module
runs), clicks the counter, and checks the new value.

### Errors

Every refusal carries `file:line:col`, says what React would have done, and
names the subset's alternative. Examples: `useEffect` in a server component →
"move it into a `"use client"` component"; a component defined inside render
→ "define it at module level"; React context → "pass props, or use
`sharedState` in client components".

## The old path

- **Until the cutover, pages keep building through `packages/pages`.** The
  slices before it compile only `zero/components/`, and test them by calling
  the compiled functions directly. Every project with `pages/`, including
  converted 0.8 projects, still goes through `zero-pages build` and
  `zero/pages.json`, and `src/pages.rs::check` keeps requiring that artifact.
  No project changes path before the cutover, so there is no "which path"
  rule to get wrong.
- **One cutover PR** switches routes to the compiled renderer, rewrites
  `examples/full-site` in the rendering.md style and deletes the old path
  (below). There is no compatibility layer for `@spacefast/zero-pages` pages.
- **The 0.8 converter moves in that same PR.** `zero migrate app --from
  zero-0.8` (`src/config_migrate/app/pages.rs`) emits `@spacefast/zero-pages`
  pages today. The cutover PR changes it to emit pages for the compiled
  renderer (and its report stops telling owners to run `zero-pages build`),
  and keeps `tests/app_migrate.rs` green. Until then the converter is
  untouched.
- **The old path keeps its end-to-end coverage until it is deleted.**
  `examples/full-site` drives `tests/wp/hosted-pages-run.sh`, the
  `host_feature` capture tests and CI's `zero/pages.json` freshness check.
  Since the cutover rewrites the example and deletes the old path in one PR,
  that coverage changes in the same commit as the code it covers.
- **Routing, Page records, head and asset handling** stay in
  `runtime/pages/Plugin.php` and `Routes.php` until workstream 6. The compiled
  renderer replaces only how a route's body is produced.

## Deleted once this lands (build-plan §5)

- `packages/pages`'s `symbolic.ts`, the request-data refusals in `check.ts`, and
  `zero-pages build`;
- `Renderer.php`'s token and region machinery (its escaping policy, island SSR
  call and routes stay);
- `zero/pages.json` and the capture checks in `src/pages.rs`;
- `load()`, `<Show>`, `orElse()`, `count()` and `<Island>`;
- `docs/design-pages-and-agents.md` §4.3's block-region output model.

## Alternatives rejected

- **Widen the placeholder proxy.** A proxy records reads. It can't evaluate
  `&&`, `?:` or a method call on a value it doesn't have, which is why the
  2026-11-04 record said that widening it means moving onto the compiler.
- **Run JavaScript per request.** Boxes have no JavaScript, and adding a JS
  engine to WordPress would mean a second runtime to secure and to keep in
  step with PHP.
- **IR → block markup with PHP regions** (`docs/design-pages-and-agents.md`
  §4.3). It serializes every subtree twice and needs a generated dynamic block
  per conditional or loop.
- **PHPX, xph and similar JSX-in-PHP projects.** They take PHP expressions in
  the template, not TypeScript, so they share nothing with the compiler.
- **React Compiler.** It memoizes React components. Its IR models React's
  reactive scopes, it is tied to Babel, and it has no other target.
- **React `hydrateRoot` in the browser.** It needs byte-identical markup and
  doesn't patch attribute differences. The Interactivity API ships with
  WordPress and takes over server HTML in place.

## Order of work

1. This record.
2. IR nodes for elements, fragments, expression containers and component
   calls, which replace both JSX refusals.
3. Generator A with `\Zero\Html` and React's child rules; `&&`, `?:`, `??`,
   `.map`, `.length` and method calls on request data; async server components.
4. Node-vs-PHP HTML parity cases in `tests/differential/` and
   `tests/compiler.rs`.
5. Generator B for `"use client"`, and the browser check.
6. The cutover, in one PR: `examples/full-site` rewritten in the rendering.md
   style, including a `"use client"` counter, compiled and passing parity; the
   0.8 converter's page output moved onto the compiled renderer; and the
   deletion above.
