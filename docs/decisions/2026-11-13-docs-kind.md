# A docs section is a hierarchical kind synced from a folder of Markdown

Date: 2026-11-13. Status: accepted. Spec: [spec.md](../spec/spec.md) §1 (`content/` is "markdown/JSON
synced into kinds"), §2.6 (`hierarchical`, `sync`), §2.7 (`:path`).

## Problem

A documentation site is a folder tree of Markdown with an order: sections, pages inside them,
previous and next, a table of contents per page. Frameworks like it usually add a second content
system for that (a loader over `content/docs/**` with its own metadata files). First already has
one: `content/` files sync into kinds, and a kind is what an editor changes in wp-admin.

## Decision

**A docs section is a kind.** No second content system.

```ts
export const docs = collection(
  { title: text(), slug: slug({ source: "title" }), content: richText().optional() },
  { hierarchical: true, url: "/docs/:path", sync: "content/docs/**/*.md" },
);
```

- **`hierarchical: true`** is WordPress's own hierarchical post type. The compiler adds two fields,
  `parent` (a reference to another item, or null) and `order`, stored as the post's `post_parent`
  and `menu_order`, so the block editor's page attributes panel edits them and core's
  `get_page_by_path` resolves a `:path` URL.
- **`sync: "content/docs/**/*.md"`** reads the folder tree. The path is the structure:
  - a file's name is its slug; its folder is its parent;
  - a folder's `index.md` is the item the folder stands for (`guides/index.md` is `/docs/guides`);
  - neither slug nor parent is written in front matter, so moving a file moves the page;
  - `order` is front matter, as every other field; siblings with the same order sort by title.

  There is no per-folder metadata file: the folder's `index.md` holds its title and order, as any
  page does. One concept, one declaration.
- **`first sync`** carries it both ways. A page an editor moves in wp-admin moves its file on the
  next pull; a page that gains children becomes its folder's `index.md`.
- **`"first/content"`** gives a page the navigation, from the published tree as the visitor may
  read it:
  - `nav(kind, current)`: the tree, siblings by order then title, the current item and its
    ancestors marked (four levels; the type system has no recursive types);
  - `pager(kind, current)`: the items before and after, reading the tree top to bottom;
  - `headings(item)`: the `##` and `###` headings with their anchor ids. The same render gives the
    page's headings those ids, so table-of-contents links land.

  They read through the query API as the visitor. The tree holds published items only, also for
  an editor who could read drafts, so navigation is the published site and the same page is the
  same for everyone it is cached for.

## Alternatives not taken

- **A content loader with `meta.ts` per folder** (Blume, Fumadocs): a second store beside the kinds,
  invisible to wp-admin, and a second set of rules for drafts and access.
- **A per-folder section file** for title and order: the folder's `index.md` already is the page
  the folder stands for; a second file would split one item's fields across two files.
- **`parent` and `order` as ordinary fields in postmeta**: possible today with `ref(() => docs)`,
  but WordPress would not see a tree, `:path` would not resolve, and the editor's page attributes
  would not edit it.

## Cost

- A docs page's slug is unique in its kind, as WordPress requires for one post type: two folders
  can't both have an `install.md`. The build says which two files collide.
- `nav()` reads at most 2,000 items per kind and request.
- The built-in `wp.pages` kind is hierarchical too; when the authoring work lands it, the same
  helpers apply to it.
