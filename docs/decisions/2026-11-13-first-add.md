# `first add <module>`: optional parts arrive as files the author owns

Date: 2026-11-13.

A new project starts with WordPress content only. SQL tables, and later pages and agents, are parts
a project adds when it needs them. `first add <module> [dir]` is the one command that adds a part.
`db` is the first module.

## Rules every module keeps

1. **A module is files, not a switch.** `first add db` writes ordinary source files and nothing
   else: no flag in `first.config.ts`, no entry in a lock, no package. The compiler already reads
   every `.ts` file under `first/`, so the files are the feature. Deleting them removes it.
2. **It only creates.** A path that already holds anything (a file, a directory, a link that points
   nowhere) is kept as it is and reported as kept. There is no `--force`. Running the command again
   adds whatever is missing and changes nothing else, so it is safe to rerun.
3. **It never edits a file it didn't create.** `first.config.ts`, `tsconfig.json` and `package.json`
   are the author's. Where a module needs a line in one of them, its own files say which.
4. **The project compiles before and after.** The command compiles the project in memory first and
   refuses a project that doesn't compile, with that project's own error, before writing anything.
   After writing it compiles again. If the new files break the build (an export name the app already
   uses), every file and directory the run created is removed and the error is shown. A file that
   could not be written whole is removed the same way.
5. **An example is for a project that lacks the part.** A file can say when it belongs: always, only
   while the project has none of the module's kinds, or only when the kinds it calls exist. A project
   with its own tables gets the note but not two more tables, and never client code for tables it
   doesn't have. A file left out is reported as skipped, with the reason.
6. **The module's files explain themselves, and what they show is safe to copy.** Each module writes
   a commented example that compiles and a short note in `first/` on how the part works. An access
   rule in an example refuses a signed-out visitor first: a rule function that returns a filter
   admits every caller the filter matches, signed in or not.

## What `db` writes

| File | Holds |
|---|---|
| `first/tables.ts` | two `table()` kinds joined by a `ref()` (a foreign key and the relation in both directions), with access rules as roles and as a function that returns a filter. Written only while the project has no `table()` |
| `tables.client.ts` | the example tables through the generated typed client. Written only when the project has both example tables |
| `first/DATABASE.md` | collection or table, the migrations folder, what the deploy check refuses, where to read and write |

`tables.client.ts` is at the project root because every `.ts` file under `first/` is app code
compiled to PHP, and a browser client is not.

## Adding a module

One row in `MODULES` in `src/commands/add.rs` (name, summary, files with their conditions, next
steps) and the files under `src/commands/add/<name>/`. The command table row in
`runtime/First/Cli/commands.json` names the modules in its summary, and `tests/cli.rs` fails when a
module is missing from it. The same suite runs the command on a fresh scaffold and serves the result
on WordPress; add the new module's run there.

The scaffold's `tsconfig.json` includes `first/**/*.ts` and `*.client.ts`, so a module's files are
type-checked in a new project without an edit.
