# Comments: the component shows, the kind decides

## Problem

`<Comments for={item} />` (rendering.md §4.5) renders a thread and a form. The
spec puts the comment options on the kind (`comments: true | { guests?,
moderation?, threaded?, closeAfterDays?, types? }`, spec §2.3) and has First
enforce them where comments are written. Comments reach a site three ways: the
component's form, the API (`POST /__first/api/v1/comments`, core's
`/wp/v2/comments` under it), and core's `wp-comments-post.php`, which the core
comment blocks post to on a WordPress-rendered site.

## Decision

**No policy props.** The component takes `for` and `className` only.

- A prop is something the page says, and the create path can't know or trust
  it.
- If `guests` were a prop, either the API believes the page, so anyone can post
  as a guest by calling it directly, or it ignores the prop, so the prop lies.
- Policy lives where it is enforced: on the kind.

**One enforcement point, on core's public hooks** (`runtime/First/Wp/Comments.php`).
The three paths therefore give the same answer:

- `pre_comment_on_post` covers `wp-comments-post.php`, before anything is saved.
- `preprocess_comment` covers every caller of `wp_new_comment`.
- `rest_pre_insert_comment` covers the REST controller, which the API
  dispatches to.
- `pre_comment_approved` makes the moderation decision, after core's own checks.
- `comments_open` (in Hardening) keeps comments closed on kinds that don't turn
  them on.
- `rest_allow_anonymous_comments` stays core's `false`.

Comments are created through core's own path, so duplicate and flood checks,
Akismet when the site has it, and notifications behave as on any WordPress site.

**The app's policy, never the Discussion settings.** No Discussion option is
read as the source of truth. A site admin who sets "hold every comment" or turns
off "users must be registered" changes nothing an app declared; the test turns
both on to check this.

**`comments: true` is the spec's defaults** (an options object changes any of
them: `guests`, `moderation` as `"none" | "first-time" | "all"`, `threaded`,
`closeAfterDays` counted from the item's publish date; the enforcement point reads
them through `First\Schema::commentPolicy()`):

- **Signed in only.** A signed-out visitor sees approved comments and a sign-in
  link, and every path answers 401. With `guests: true` a signed-out visitor may comment, and gives a name
  and a valid email on every path whatever WordPress's `require_name_email` says.
- **First-time moderation.** A commenter with an approved comment anywhere on
  the site is approved at once; otherwise the comment is held. Users who may
  moderate are approved, as core does.
- **Threaded to depth 3.** A reply below depth 3 is **refused** (400, "Replies
  go 3 levels deep here."), not flattened. A flattened reply would show
  somewhere its author didn't put it, answering a different comment, and the
  three paths would have to agree on where it moves. The component offers no
  reply form at depth 3.
- **Never closed.**

**Reads.** The thread is the approved comments plus the visitor's own held ones,
marked as awaiting moderation. It is read only when the visitor may read the
item: the component checks the item's read rule again, and the API's comment
list answers 403 for an item the visitor can't read. A signed-out render shows
only approved comments, so the page stays shared. A signed-in render is already
`private, no-store`.

**Page caches follow the thread.** A comment event that changes what visitors see
of a thread (approved, unapproved, spammed, trashed, deleted, or edited while
approved; `Comments::visible()` decides) purges the item's URL, its Markdown
twin and comments feed, and every cached page that rendered that item (the
page cache's read index, the exact item only). A held or spam submission purges
nothing. Pages that only list the kind keep their copy, so a comment count shown
on a listing updates within the cache window.

**The form works without JavaScript** through the forms mechanism
([2026-11-14](2026-11-14-forms-without-javascript.md)): it posts form-encoded to
`POST /__first/api/v1/comments` and comes back with a 303 and a flash. It shows
the refusal, or the "awaiting moderation" notice.

**The kind is found at build time** from the type of `for`: it must be a row of
exactly one collection, and that collection must turn `comments` on. Otherwise
the build stops at the prop with the option to set.

## Not in this slice

- `guests`, `moderation`, `closeAfterDays` and `types` as options.
- Comment types (`wp.comments.type`).
- Update and delete.
- `wp.comments` in `"first:db"`.

The kind's options arrive as their own slice. `Comments::policy()` then reads
them, and neither the component nor the enforcement point changes shape.

## Costs

- A refused deep reply asks the commenter to reply higher up the thread.
- First-time moderation counts approved comments across the site, as core's
  "previously approved" check does, not per kind.
