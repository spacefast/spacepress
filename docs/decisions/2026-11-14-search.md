# `<Search>` and `<SearchResults>`

Date: 2026-11-14. Status: accepted.

## Context

Apps on First need a site search that works without JavaScript and that respects the same access rules as every other read. The search index (`docs/decisions/2026-11-13-search-index.md`) already turns a query into a condition on a kind's own read, so the read rule, drafts and field access apply.

## Decision

- Two components. `<Search>` is a plain `GET` form with `q` (never `s`, which would start WordPress's own search query). `<SearchResults>` reads `kind.findMany({ search })` and `count` as the visitor.
- A result is the row's title linked to its kind's URL, and nothing else: no excerpt, so no snippet can show text from a field the visitor may not read. A kind without a `url` is refused at build time when named, and left out of the site-wide search.
- Site-wide results are grouped per kind, up to `perPage` each, with a link to the rest at `kind=<name>`. There is no pagination across kinds.
- A render with a non-empty `q` is private (`private, no-store`), `noindex`, and not recorded in the page cache's read index. Shared caching of results would be correct, but each distinct query would be one more cached URL that lists the kind, and enough of them would turn every write to the kind into a whole-host purge.
- Queries longer than the index allows (200 characters) show a message, never an error page.
- Suggestions while typing are a separate step, on top of this.

## Costs

- Every search is an uncached render. Sites with heavy search traffic pay for it at the origin.
- No snippets: a visitor sees titles only.
- The function-child form (render each row yourself) isn't offered, since server components take no function children; `kind.list({ search })` in the page covers that case.
