2What you write

Everything lives in tp/. A thing is declared once and named by its export. File names inside tp/ are yours to choose, except app/.

my-site/
  typedpress.config.ts     site name and switches
  tp/
    schema.ts              kinds: what your data is
    server.ts              queries, mutations, jobs, event handlers
    app/                   optional pages
    content/               optional Markdown, kept in step by sync
    _generated/            types, client types, migrations (never edit)

Kinds Built

// tp/schema.ts
import { collection, table, taxonomy, text, richText, integer, ref, media } from "typedpress";

export const authors = collection({
  name: text().max(80),
  avatar: media({ accept: "image" }).optional(),
});

export const posts = collection({
  title: text().max(200),
  body: richText(),
  writer: ref(authors),
  views: integer().default(0),
}, { url: "/blog/:slug", access: { read: "anyone", create: "editor" } });

export const topics = taxonomy({ color: text().optional() }, { url: "/topics/:slug", on: [posts] });

export const likes = table({ post: ref(posts), count: integer().default(0) });

Event handlers Ruled

main has the object form .on({ beforeCreate }), in the declaring file only. The ruled form is one handler per call, from any file:

// tp/server.ts
import { posts } from "./schema";

posts
  .on("beforeCreate", (data) => { data.title = data.title.trim(); })
  .on("change", async (c) => { await audit.system.create({ op: c.op, row: (c.after ?? c.before)!.id }); })
  .on("committed", async (c) => {
    if (c.op === "publish") await notifySubscribers.enqueue({ postId: c.after!.id });
  });
EventRunsCan change dataIf it throws
beforeCreate, beforeUpdatebefore the writeyeswrite is rejected
beforeDeletebefore the deletenodelete is rejected
afterCreate … afterUnpublishafter the write, same transactionnotransaction rolls back
changeonce per write, with { op, before, after }notransaction rolls back
committedafter commit, as a queued action, retriednoretried; the write stays
  • Every write path runs every handler: the API, the WordPress editor, the CLI and jobs.
  • A handler runs as the person who made the write. .system is the only bypass.
  • Proposed c.source says where the write came from: api, editor, cli, job or agent. Idea from the UI SDK's change details.

Server functions Ruled

main has action({ input, handler }). The ruled form splits reads from writes and takes input types from the handler:

import { query, mutation, job, cron, HttpError } from "typedpress";

export const popular = query({ access: "anyone" },
  async ({ limit = 10 }: { limit?: number }) =>
    posts.list({ orderBy: { views: "desc" }, limit }));

export const like = mutation({ access: "subscriber", rateLimit: "10/min" },
  async ({ id }: { id: number }) => {
    const post = await posts.get(id);
    if (!post) throw new HttpError(404, "not_found", "No such post");
    await posts.system.update(id, { views: post.views + 1 });
  });

export const notifySubscribers = job({}, async ({ postId }: { postId: number }) => { /* … */ });
export const nightly = cron("0 3 * * *", async () => { /* … */ });

Pages (optional) Built

// tp/app/blog/[slug]/page.tsx
import { Content, notFound, type PageProps } from "typedpress/app";
import { posts } from "../../../schema";
import { LikeButton } from "./LikeButton";

export default async function Post({ params }: PageProps<"blog/[slug]">) {
  const [post] = await posts.list({ where: { slug: params.slug }, limit: 1 });
  if (!post) notFound();
  return (
    <article>
      <h1>{post.title}</h1>
      <Content value={post.body} />
      <LikeButton id={post.id} count={post.views} />
    </article>
  );
}
// tp/app/blog/[slug]/LikeButton.tsx
"use client";
import { useState } from "typedpress/state";
import { like } from "../../../server";

export function LikeButton({ id, count: start }: { id: number; count: number }) {
  const [count, setCount] = useState(start);
  return <button onClick={async () => { await like({ id }); setCount(count + 1); }}>{count} likes</button>;
}

A client component is server HTML first, then the WordPress Interactivity API takes it over. It cannot import npm React components today.

12Agents: a separate add-on

Ruled (2026-11-15) Agents inside an app are secondary and are built isolated, later. One scheduling mechanism for everything. WordPress's own parts are used wherever they exist. On Spacefast the models are Spacefast's; on any other WordPress the site's Connectors supply them. What is needed now is the list of seams, so the add-on can be built without changing the core, and so people can build chat, channels and memory themselves.
