TypeScript in. A WordPress plugin out.

You describe your data and your pages in TypeScript. TypedPress compiles them into a WordPress plugin. WordPress then gives you the database, the editor, sign-in, the API and an admin, and no JavaScript runs on the server.

This is a whole app. Change it and it is built again here, in your browser, by the real compiler. The right side shows every file the build writes and what your change did to them. Run in WordPress starts a WordPress in this tab with your version installed.

Read this first. TypedPress is the new name of the framework called First. It is experimental and has no npm release yet. The guide below uses the new names; in the code today, typedpress is spelled first and the tp/ folder is first/. Everything you can edit and build on this page runs the compiler as it is today, so it uses today's names. Some spellings may still change.

The project

Everything lives in tp/. You declare a thing once and its export name is its name everywhere: in the API, the client, the admin and the database. File names inside tp/ are yours to choose, except app/. Section {{sec:examples}} has three complete projects.

my-site/ typedpress.config.ts site name and switches tp/ schema.ts kinds: what your data is server.ts queries, mutations, jobs, event handlers app/ optional pages and HTTP routes content/ optional Markdown, kept equal to the site by sync _generated/ types, the typed client, migrations (never edit)

How it works

You write TypeScript. A compiler turns it into a WordPress plugin once, at build time. After that, WordPress runs the plugin and nothing else: there is no Node process, no JavaScript engine and no second database on the server.

StepWhat happensWhere it runs
1. You writekinds, functions, pages and components in tp/your editor; the TypeScript compiler checks it
2. typedpress buildthe compiler reads every file under tp/, checks that the server code stays inside the subset it can translate, and writes PHP, SQL migrations, an OpenAPI document, typed client files and small browser scriptsyour machine or CI
3. Deploythe plugin is uploaded; pending schema changes are checked against the live rows, then appliedthe site
4. A request arrivesWordPress routes it. A page is rendered by the compiled PHP as the person viewing it. An API call runs the compiled function inside one database transactionPHP, on the site
5. An editor savesthe WordPress editor writes the same rows, through the same access rules and the same handlersPHP, on the site
6. Background workjobs and schedules are queued in the same transaction as the write and run after it commitsAction Scheduler, the queue WordPress sites already use
7. In the browserpages arrive as HTML. Only "use client" components ship a script, and they run on the WordPress Interactivity APIthe visitor's browser

Access rules

Each of read, create, update and delete takes one of these:

ValueMeaning
"anyone"everyone, signed in or not
"authenticated"anyone signed in, guests included
"guest" < "subscriber" < "author" < "editor" < "admin"that role or a higher one
"self", "owner"the signed-in user's own row, or the uploader of a file
(ctx) => boolean | filteryour own rule; a returned filter narrows what the user can read or change

These rules are the only gate, on every way into the data: the TypedPress API, WordPress's own REST API, the admin, the editor and agent tools.

When the schema changes

Works today You never write a migration. The build compares the schema with the last build and writes the SQL. At deploy, every pending change is checked against the live rows before any of them runs.

ChangeResult
a new kind, a new optional field, a field with a default, a new indexapplies
a field becomes required and has a defaultrows without a value get the default, then it applies
a field becomes required, no default, and rows lack itrefused, with the row count
a kind or field that holds rows is removedrefused, with the row count, until the deploy names it explicitly
a rename.was("oldName") keeps the rows

Read and write data

Works today Inside pages, queries and mutations, a kind reads and writes as the visitor: access rules, drafts and hidden fields apply automatically.

import { posts } from "typedpress:db"; await posts.list({ where: { writer: { name: "Alice" } }, // filter through a relation orderBy: { views: "desc" }, limit: 10, with: { writer: true, topics: true }, // load related rows }); await posts.paginate({ limit: 20, cursor }); // { rows, cursor } await posts.get(42); // the row, or null await posts.get({ slug: "hello" }); await posts.count({ search: "tea" }); // full-text search on what the visitor may read await posts.create({ title: "Hi", writer: 3 }); await posts.update(42, { title: "Hello" }); await posts.delete(42); await posts.system.list(); // trusted: no access rules, every draft // staged versions, through the client: change a published item without visitors seeing it await tp.posts.stage(42, { title: "New title" }); await tp.posts.compare(42); // what differs from the live item await tp.posts.promote(42); // or promote(42, { at: "2026-12-01T09:00:00Z" }) await tp.posts.discard(42); // languages await posts.create({ locale: "de", translationOf: 42, title: "Hallo" }); await posts.list({ locale: "de" }); // German rows, falling back to the default language
  • Filters on a list of links: { tags: { has: 5 } }, { tags: { name: "news" } }, { tags: [] } for none.
  • A request, a mutation and a job each run in one transaction that covers table rows and WordPress content together.
  • .system is the only way around the rules. Jobs and signed webhooks have no visitor and run as the system.
  • Search uses an index TypedPress keeps current on every write. A draft or a hidden field is never found and never counted.

Server functions, jobs and routes

Queries and mutations Decided

A query reads, a mutation writes. Input types come from the handler's own parameter. Works today as one form, action({ input, handler }).

import { query, mutation, job, cron, HttpError } from "typedpress"; export const popular = query({ access: "anyone" }, async ({ limit = 10 }: { limit?: number }) => posts.list({ orderBy: { views: "desc" }, limit })); export const like = mutation({ access: "subscriber", rateLimit: "10/min" }, async ({ id }: { id: number }) => { const post = await posts.get(id); if (!post) throw new HttpError(404, "not_found", "No such post"); await posts.system.update(id, { views: post.views + 1 }); });
querymutation
May writenoyes, in one transaction
Cached and subscribableyesno
After it runsnothingpurges the pages its writes changed
As an agent toolmarked read-onlymarked as a write
As a form actionnoyes, and it works without JavaScript
  • From the browser you call a function by its export name: tp.popular({ limit: 5 }), tp.like({ id }).
  • From server code you import it and call it. It runs as the current caller with its access check, and as the system inside a job.
  • Default access is "editor". A mutation open to "anyone" gets a default rate limit. Limits count per user, or per address when signed out.
  • A mutation accepts an idempotency key, so a retried call does not write twice.
  • Every function, handler and route gets one ctx: ctx.user, ctx.can(op, kind, row?), ctx.env, and ctx.request in routes.
  • Errors carry field messages. A refused write answers a standard problem document with fields, a map from field name to message, so a form can show each message beside its field.
  • Old pages after a deploy. A call to a function the new build removed answers 409 stale_client and the client reloads the page. .was("oldName") keeps an old name answering for one release.

Proposed In the browser, useMutation on ask sends a message and useQuery on thread shows the replies as they arrive.

The rules an agent runs under

  • It always acts as a WordPress user. A run started by a signed-in person acts as that person. A run started by a schedule acts as the account named in runAs, which may not be an admin. It never runs with the trusted access that .system gives.
  • It can call only the tools it lists. Each call passes the same access rules as a call from the browser.
  • It has a turn limit, and a failed run is retried the way a failed job is.
  • The project holds no model key. If the site has no model set up, the run fails with a message that says so.

What is particular to TypedPress

  • No JavaScript on the server. Of the systems above that let you write server code in TypeScript, each runs it on a JavaScript runtime. TypedPress compiles it to PHP, so the server is a plain WordPress site.
  • An editor that already exists. The editing screens are WordPress's own. Payload, Sanity, Strapi and EmDash each ship an admin of their own.
  • One rule on every way in. A kind's access covers the API, WordPress's own REST API, the editor, pages, search and agent tools. Payload is the closest: its access functions also return yes, no or a filter, and its documentation says the server-side Local API skips them unless told not to. The others write access per function, keep it in a separate rules language, or fix it to roles.
  • Content and app data in one transaction. A write to a post and a write to your own table commit together.

What it gives up

  • npm packages on the server. TypedPress server code is compiled to PHP, so it cannot import arbitrary npm packages; a few small ones are tested one by one. Systems that run JavaScript on the server do not have this limit.
  • Push by default. Convex keeps a WebSocket open and sends each change to the browser. TypedPress polls unless the host adds a push transport.
  • A choice of database. Payload, Strapi and EmDash support several. TypedPress uses the database WordPress uses.
  • React on its own pages. A TypedPress page is not a React app. For React components from npm, build a separate front end and use the client.
  • Maturity. Every system above has releases you can install. TypedPress is experimental and has no npm release.

What it does not do

  • npm packages on the server. Server code is compiled to PHP, so it cannot import arbitrary npm packages. A few small ones are tested one by one.
  • React components from npm inside TypedPress pages. Use them in a separate React frontend with the client (section {{sec:frontend}}).
  • Any theme or plugin you like. One built-in theme, and plugins only under the rules in section {{sec:rules}}.
  • Agents inside the app. Designed as a separate add-on, not built (section {{sec:app-agents}}).
  • A push transport for live reads. Live reads poll unless the host adds one.
  • Several apps on one site. One app per site today; on a WordPress network, one per site of the network.
  • Compiling on the site. A deploy sends a build compiled on your machine.
  • Undoing a migration. Going back to an earlier version switches the code, not the database.
  • A stable API. The framework is experimental. Names and shapes on this page will change before a first release.
